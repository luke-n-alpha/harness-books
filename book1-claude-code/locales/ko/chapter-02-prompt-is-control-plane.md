# 2장 프롬프트(prompt)는 인격이 아니라 제어 평면(control plane)입니다

## 2.1 프롬프트를 인격으로 취급하는 것은 흔한 오해입니다

시스템 프롬프트(system prompt)라는 말이 나오면 많은 사람이 가장 먼저 익숙한 수사들을 떠올립니다. 당신은 누구인지, 무엇을 잘하는지, 그리고 가급적 안정적인 인격을 갖추는 것이 좋다는 내용입니다. 대화형 시스템에는 이런 이해로 충분할지 모르지만, 파일을 읽고 도구를 호출하며 셸(shell)을 조작하고 턴(turn)을 넘나들며 실행되는 에이전트(agent) 시스템에는 확실히 부족합니다. 인격은 '그것이 무엇처럼 보이는가'를 해결하고, 제어 평면(control plane)은 '그것이 무엇을 할 수 있고, 언제 하며, 잘못되면 어떻게 처리하고, 누가 뒤를 봐줄 것인가'를 해결합니다. 둘은 같은 층위의 문제가 아닙니다.

Claude Code의 구현은 이를 잘 보여줍니다. 시스템 프롬프트는 인물의 약전(biography)이 아니라 런타임 프로토콜(runtime protocol) 세트에 가까운, 계층적으로 조립된 행동 블록들입니다.

## 2.2 소스 코드로 볼 때, Claude Code의 프롬프트는 처음부터 계층화되어 있습니다

`src/constants/prompts.ts:444`에 있는 `getSystemPrompt()`에서 Claude Code는 완성된 문자열 하나가 아닌, 여러 섹션으로 구성된 배열을 반환합니다. 이 디테일은 중요합니다. 프롬프트가 여러 개의 블록으로 구성되는 순간, 시스템은 내부적으로 각기 다른 책임을 가진 제약 조건들의 집합이 포함되어 있음을 공식적으로 인정하는 것이기 때문입니다.

이러한 섹션들은 적어도 몇 가지 종류의 내용을 포함합니다.

우선 신원과 총괄 임무 설명입니다. `src/constants/prompts.ts:175`에서 시스템은 자신이 대화형 에이전트이며, 사용 가능한 도구를 활용해 소프트웨어 엔지니어링 과업을 완수하도록 돕는 존재라고 설명합니다. 여기에는 URL을 함부로 추측하지 말라는 등의 안전 제약 조건도 함께 포함되어 있습니다.

다음은 시스템 수준의 규칙입니다. `src/constants/prompts.ts:186`부터 시스템은 다음 사항을 명시합니다.

- 사용자가 볼 수 있는 텍스트는 무엇인가
- 도구 호출 시 권한(permission) 승인이 트리거될 수 있음
- 사용자가 거부한 경우 기계적으로 재시도해서는 안 됨
- 도구 결과(tool result)와 사용자 메시지(user message)에 시스템 알림(system-reminder)이 섞일 수 있음
- 컨텍스트(context)는 자동으로 압축(compaction)됨

이 내용들에는 뚜렷한 특징이 있습니다. 모델이 '똑똑한 비서처럼 보이는가'에는 관심이 없고, 규정을 잘 지키는 실행체(executor)인지에만 관심이 있다는 점입니다. 이것이 바로 제어 평면의 어조이며, 그 핵심 임무는 경계를 정의하는 것입니다.

그 아래, `src/constants/prompts.ts:199`부터는 과업 수행 시의 엔지니어링 지침이 나옵니다. 요구 사항을 임의로 추가하지 말 것, 권한을 넘어서서 최적화하지 말 것, 결과의 완결성을 위해 검증 실패를 숨기지 말 것, 필요하지 않은데 추상화를 만들지 말 것 등입니다. 이런 내용들은 글쓰기 스타일 요구 사항처럼 보이지만, 사실 엔지니어링 제약 조건과 긴밀하게 결합되어 있습니다. 제품 관점에서는 '알아서 모든 것을 척척 최적화하는' 모델이 열정적으로 보일지 모르나, 엔지니어링 관점에서는 상당히 위험합니다.

즉, 소스 코드 구조만 보아도 알 수 있듯이, Claude Code의 프롬프트가 해결하려는 것은 복잡한 런타임 속에서 어떻게 모델이 경계를 준수하게 할 것인가 하는 문제입니다.

## 2.3 프롬프트의 진정한 가치는 텍스트 자체가 아니라 우선순위에 있습니다

프롬프트가 단순히 텍스트로 쓰여 있는 것만으로는 충분한 설명이 되지 않습니다. 그것이 제어 평면에 속하는지 결정하는 진정한 요소는 시스템이 엄격한 우선순위를 정의했는지 여부입니다.

이 점은 `src/utils/systemPrompt.ts:28`부터 시작되는 `buildEffectiveSystemPrompt()`에서 확인할 수 있습니다. 이 코드는 프롬프트의 출처를 명확하게 하나의 체인으로 정렬합니다.

1. 오버라이드 시스템 프롬프트(override system prompt)
2. 코디네이터 시스템 프롬프트(coordinator system prompt)
3. 에이전트 시스템 프롬프트(agent system prompt)
4. 사용자 정의 시스템 프롬프트(custom system prompt)
5. 기본 시스템 프롬프트(default system prompt)

마지막으로 `appendSystemPrompt`를 일괄적으로 이어 붙입니다.

여기서 프로액티브 모드(proactive mode) 처리는 더 직관적입니다. `src/utils/systemPrompt.ts:99` 이후를 보면, 에이전트 프롬프트와 프로액티브 모드가 동시에 존재할 때 에이전트 프롬프트는 기본 프롬프트를 대체하지 않고 그 뒤에 부착됩니다. 일반적인 제도는 직무 기술서로 보완할 수는 있지만, 직무 기술서에 의해 직접적으로 뒤엎어져서는 안 됩니다.

### 뼈대: 프롬프트 조립의 우선순위 체인 (skeleton)

```
// skeleton: buildEffectiveSystemPrompt()  (src/utils/systemPrompt.ts:28)
sources = [override, coordinator, agent, custom, default]
base = first_present(sources)           // 높은 우선순위의 소스가 기본값을 통째로 대체
if proactive_mode and agent:
    base = default + agent              // 특례: 대체가 아닌 중첩
return base + appendSystemPrompt        // 추가(append)는 항상 마지막 층

assert exists unique base in sources                # 기준선은 반드시 유일해야 함
assert precedence(override) > precedence(default)   # 순서는 하드코딩, "나중에 쓴 것이 우선" 방식 아님
assert appendSystemPrompt never replaces base       # 추가는 오직 덧붙이기만 가능
```

이 세 가지 불변 조건 중 하나라도 파괴되는 순간, 프롬프트는 나중에 쓴 사람이 장땡인 낙서장으로 퇴보하게 됩니다.

## 2.4 프롬프트는 정적인 문구가 아니라 메모리 시스템과도 연결됩니다

앞서 언급한 내용들이 이미 런타임 설명서 같다면, Claude Code가 메모리(memory)와 `CLAUDE.md`를 처리하는 방식을 보면 이곳의 프롬프트가 단순히 '모델에게 보여주는 한 문단'을 넘어 전체 컨텍스트 거버넌스(context governance)의 입구임을 더 명확히 알 수 있습니다.

`src/utils/claudemd.ts:1153`의 `getClaudeMds()`에서 시스템은 프로젝트 지침, 로컬 지침, 팀 메모리, 자동 메모리(auto memory) 등 서로 다른 출처의 내용을 통합된 형식으로 정리하여 프롬프트 관련 컨텍스트에 병합합니다. 여기에는 각 내용의 출처 설명(프로젝트 수준 지침, 사용자 개인 프로젝트 지침, 공유 팀 메모리, 혹은 세션을 넘나들며 유지되는 자동 메모리 등)까지 매우 세밀하게 적혀 있습니다.

또한 `src/memdir/memdir.ts:187`부터 시작되는 `buildMemoryLines()`에서는 '메모리를 어떻게 저장할 것인가'라는 과정 자체를 프롬프트의 일부로 만듭니다. 시스템은 모델에게 다음을 명확히 전달합니다.

- 메모리는 파일 기반의 영속성 시스템임
- `MEMORY.md`는 색인(index)이며 본문이 아님
- 프런트매터(frontmatter)를 어떻게 작성해야 하는지
- 어떤 정보는 저장해서는 안 되는지
- 계획(plan)과 작업(task)이 메모리로 오용되어서는 안 됨

이는 매우 중요한 점입니다. 프롬프트의 책임을 '현재 행동의 제약'에서 '미래 지식의 침전 방식을 제약'하는 것으로 확장합니다. 이는 통상적인 프롬프트의 의미를 넘어 런타임 참여자를 위한 지식 거버넌스(knowledge governance) 프로토콜에 더 가깝습니다.

바꿔 말하면, Claude Code는 '이번 턴에 어떻게 말할 것인가'를 규정하기 위해 프롬프트만 사용하는 것이 아니라, '장기 기억을 어떻게 형성할 것인가'를 규정하기 위해서도 프롬프트를 사용합니다. 시스템이 이 단계까지 이르면 프롬프트는 더 이상 어조의 문제가 아니라 필연적으로 제도(institution)의 문제가 됩니다.

## 2.5 진정한 제어 평면은 캐싱과 컴퓨팅 비용도 고려해야 합니다

대부분의 사람들은 프롬프트를 이해할 때 성능을 거의 고려하지 않습니다. 흔히 프롬프트는 모델에게 공급되는 텍스트일 뿐이니 잘 쓰기만 하면 된다고 생각합니다. Claude Code의 구현은 더 실용적입니다. 프롬프트는 컴퓨팅 비용이기도 합니다. 프롬프트가 복잡하고 변화가 빈번할수록 캐시 적중률(cache hit rate)은 떨어지고, 시스템 실행은 더 비싸고 느려집니다.

`src/constants/systemPromptSections.ts:16` 이후를 보면 시스템은 프롬프트 섹션을 두 부류로 구분합니다.

- 캐시 가능한 `systemPromptSection`
- 캐시를 깨뜨리는 `DANGEROUS_uncachedSystemPromptSection`

그리고 `resolveSystemPromptSections()`는 캐시에서 이미 계산된 내용을 우선적으로 가져오며 필요할 때만 다시 계산합니다. `clearSystemPromptSections()`에서는 `/clear`나 `/compact` 이후 이러한 상태들을 초기화합니다.

이것이 최적화처럼 보이지만, 실제로는 제어 평면의 영역입니다. 진정으로 운용 가능한 프롬프트 시스템이라면 표현 능력뿐만 아니라 처리량(throughput), 지연 시간(latency), 캐시 영향도를 고려하지 않을 수 없습니다. Claude Code는 `getSystemPrompt()`에서 정적 부분과 동적 부분을 경계(boundary)를 사용하여 명시적으로 분리해 두었습니다(`src/constants/prompts.ts:560` 이후 참고). 이는 설계 단계에서 세션 중에 상대적으로 안정적인 내용과 매 턴 변하는 내용이 존재함을 인정하고, 이 둘을 한데 섞어서 캐시를 소모하게 해서는 안 된다는 점을 인지했음을 의미합니다.

엔지니어링 시스템이 '프롬프트의 어떤 부분이 캐시를 무효화하는가'를 신경 쓰기 시작하는 순간, 프롬프트를 더 이상 문안 창작으로 대하지 않게 됩니다. 문안은 완벽한 표현을 추구하고, 제어 평면은 거버넌스 가능성, 재사용성, 예측 가능한 행동 비용을 추구합니다. 양자가 주목하는 문제는 서로 다릅니다.

## 2.6 사용자는 프롬프트를 오버라이드할 수 있지만, 이 구조를 건너뛸 수는 없습니다

Claude Code는 사용자를 기본 프롬프트에 가두지 않습니다. 반대로 CLI는 오버라이드와 추가를 명확하게 지원합니다.

`src/main.tsx:1342` 이후를 보면 시스템은 `--system-prompt`, `--system-prompt-file`, `--append-system-prompt`, `--append-system-prompt-file` 옵션을 처리합니다. 즉, 사용자는 당연히 자신만의 규약을 가지고 올 수 있습니다.

하지만 여기서 중요한 점이 있습니다. 시스템은 오버라이드와 추가를 허용하지만, 최종 조립에는 여전히 통일된 `buildEffectiveSystemPrompt()`를 고집합니다. 이는 커스터마이징은 허용하되 질서를 포기하지 않겠다는 의미입니다. 사용자는 내용을 바꿀 수 있지만, 시스템은 구조를 유지합니다.

구조 없는 커스터마이징은 결국 또 다른 무질서로 퇴보하기 마련입니다. 오늘은 한 문단을 더하고 내일은 빼고, 모레는 어떤 에이전트가 기준 제약을 대체해버리면 시스템 행동은 점점 임시 구두 통보처럼 변해갈 것입니다. Claude Code의 선택은 사용자의 수정을 허용하되, 그 수정이 반드시 정해진 우선순위와 계층화 메커니즘 내에서 일어나게 하는 것입니다.

## 2.7 왜 여기서 프롬프트를 대사(台詞)가 아니라 헌법이라고 하는가

앞서 언급한 각 절을 함께 놓고 보면 매우 명확한 결론을 얻을 수 있습니다.

Claude Code의 프롬프트는 헌법과 같습니다.

대사란 등장인물이 무대에서 하는 말이지만, 헌법이란 권한의 경계, 책임 관계, 예외 상황 처리 방식을 규정하는 것입니다. Claude Code의 프롬프트는 여러 구조적 조건을 충족하기에 후자에 더 가깝습니다.

- 처음부터 끝까지 하나로 쓰는 것이 아니라 계층화되어 있음
- 누가 나중에 썼느냐가 아니라 우선순위가 정해져 있음
- 메모리, `CLAUDE.md`, 에이전트 지침, 모델 컨텍스트 프로토콜(Model Context Protocol, MCP) 지침 등과 함께 완전한 제어 평면을 구성함
- 단순히 텍스트를 붙이는 게 아니라 캐시와 동적 섹션 메커니즘을 가짐
- 시스템 밖의 장식물이 아니라 런타임과 긴밀하게 결합되어 있음

이것이 바로 "좋은 프롬프트를 쓰는 것"이 단독으로 다루어질 때 가치가 제한적인 이유입니다. 더 중요한 질문은 프롬프트가 시스템 내 어디에 위치하는지, 어떤 모듈과 협력하는지, 권한·상태·컨텍스트 및 장기 기억 거버넌스에 참여하는지입니다. 이러한 질문에 답하지 못한다면, 소위 '좋은 프롬프트'는 어떤 순조로운 시나리오에서 잠시 통할 뿐입니다.

## 2.8 소스 코드에서 도출할 수 있는 두 번째 원칙

이 장은 마지막으로 한 문장으로 정리할 수 있습니다.

> 프롬프트의 가치는 그것이 명확한 제어 구조 안에 포함되었는지 여부에 달려 있습니다.

Claude Code의 소스 코드는 여러 곳에서 이를 공동으로 증명합니다.

- `constants/prompts.ts`는 프롬프트를 통일된 선언문이 아닌 세그먼트화된 제어 구조로 작성합니다.
- `utils/systemPrompt.ts`는 프롬프트 출처의 우선순위를 명확히 규정합니다.
- `utils/claudemd.ts`는 프로젝트 수준 및 장기 기억 내용을 컨텍스트 조립에 포함합니다.
- `memdir/memdir.ts`는 프롬프트를 통해 장기 기억의 저장 규칙을 규정합니다.
- `constants/systemPromptSections.ts`는 프롬프트를 캐시 가능하고, 무효화 가능하며, 섹션별로 재계산 가능한 런타임 객체로 변화시킵니다.

따라서 성숙한 에이전트 시스템에서 프롬프트는 '모델을 연기하게 만드는 오프닝 멘트'로 이해되어서는 안 됩니다. 이는 운용 중인 제도 텍스트와 같습니다. 제도 텍스트 역시 명확하게 작성될 수 있지만, 가장 중요한 부분은 언제나 구속력(enforceability)입니다.

다음 장에서 다룰 내용은 또 하나의 더 단단한 뼈대인 질의 루프(query loop)입니다. 제어 평면이 아무리 좋아도 결국 실행 순환 속으로 떨어져야 하기 때문입니다. 프롬프트가 경계를 규정한다면, 순환은 운명을 결정합니다. 시스템이 결국 어떤 모습이 될지는 매 턴 어떻게 지속하고, 중단하고, 복구하는지를 결정하는 그 상태 머신(state machine) 속에 드러나게 마련입니다.
