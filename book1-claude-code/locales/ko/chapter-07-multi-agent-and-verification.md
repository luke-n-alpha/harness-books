# 7장 멀티 에이전트와 검증: 분업과 검증으로 불안정성 관리하기

## 7.1 단일 에이전트가 일정 수준에 도달하면, 문제는 "할 수 있는가"가 아니라 "어떻게 분업할 것인가"가 됩니다

단일 에이전트의 작은 모순들은 인내심으로 덮어두고 넘어갈 수 있지만, 과업이 커지면 연구(research), 구현(implementation), 검증(verification)이 동일한 컨텍스트(context) 체인에 묶여 예산, 주의력, 서사의 중심을 두고 경쟁하게 됩니다. 멀티 에이전트(multi-agent)는 자연스러운 해답처럼 보이지만, 실제로는 비용이 적지 않습니다. 제약 없는 병렬 실행은 단일 에이전트의 혼란을 복제할 뿐입니다. 진정한 어려움은 각 에이전트의 불안정성을 격리하는 동시에 결과를 다시 조직화하는 것입니다.

Claude Code의 소스 코드는 이 점을 명확히 이해하고 있습니다. 이 코드는 서브에이전트(subagent)를 "또 다른 대화창"으로 취급하는 대신, 명확한 압축(compaction) 경계, 상태(state) 경계, 검증 의무, 정리 책임을 갖춘 관리형 실행 프로세스로 다룹니다.

## 7.2 포크된 에이전트(forked agent)의 제1원칙은 캐시 안전성(cache-safe)입니다

`src/utils/forkedAgent.ts`의 시작 부분에는 Claude Code가 서브에이전트를 어떻게 이해하는지 잘 보여주는 주석이 있습니다. 이 주석에 따르면 포크된 에이전트 유틸리티의 의무는 다음과 같습니다.

1. 부모 에이전트와 캐시 중요 매개변수(cache-critical params)를 공유하여 프롬프트 캐시(prompt cache) 적중 보장
2. 전체 질의 루프(query loop)의 사용량 추적
3. 지표 기록
4. 가변 상태 격리를 통해 메인 루프 간섭 방지

이 네 가지 항목 중 가장 먼저 등장하는 것은 "캐시 중요 매개변수 공유"입니다. 이는 우연이 아닙니다. 이는 Claude Code가 포크(fork)를 런타임 차원의 제어된 분기로 간주함을 의미합니다. 분기가 발생하면 어떤 매개변수가 부모 요청과 일치해야 하는지 매우 주의해야 합니다. 그렇지 않으면 프롬프트 캐시 공유가 실패하여 비용과 지연 시간이 즉시 악화됩니다.

`CacheSafeParams`에는 다음과 같은 요소들이 명시되어 있습니다.

- `systemPrompt`
- `userContext`
- `systemContext`
- `toolUseContext`
- `forkContextMessages`

또한 `maxOutputTokens`를 함부로 변경하지 말라고 경고합니다. 사고 설정(thinking config)도 영향을 받으며, 사고 설정은 캐시 키(cache key)의 일부이기 때문입니다.

이러한 설계는 멀티 에이전트가 우선 런타임 경제학의 문제임을 시사합니다. 자식 에이전트가 매번 부모의 컨텍스트를 새로 연소시킨다면, 이는 효율성을 높이는 병렬 처리가 아니라 낭비를 병렬화하는 것에 불과합니다. Claude Code는 이 과정에서 캐시를 망가뜨리지 않는 포크 방식을 우선 처리합니다.

### 뼈대: forkAgent() (skeleton)

```
// 뼈대: forkAgent()  (출처: src/utils/forkedAgent.ts, src/utils/createSubagentContext.ts)
params = CacheSafeParams {
    systemPrompt, userContext, systemContext,
    toolUseContext, forkContextMessages        // 반드시 부모와 일치하여 프롬프트 캐시 적중 보장
}
ctx = createSubagentContext(parent):
    readFileState  := clone(parent.readFileState)              // 기본적으로 격리
    abortController := new ChildAbortController(parent)        // 자식 제어기를 부모에 연결
    getAppState    := wrap(parent.getAppState, suppress_prompt)
    setAppState    := noop                                     // 기본적으로 읽기 전용
    nestedMemoryAttachmentTriggers := new Set()
    loadedNestedMemoryPaths         := new Set()
if opt_in.shareAbortController:  ctx.abortController := parent.abortController
if opt_in.shareSetAppState:      ctx.setAppState      := parent.setAppState
hooks.fire(SubagentStart, { agent_id, agent_type })
track_usage(parent, child)
defer hooks.fire(SubagentStop,  { agent_transcript_path })     // 생명주기는 반드시 종료되어야 함
```

### 불변식 (invariants)

```
assert child.CacheSafeParams == parent.CacheSafeParams         # 포크는 프롬프트 캐시를 깨뜨리지 않음
assert child.mutable_state isolated unless opt_in.share_*       # 공유는 반드시 명시적이어야 함
assert parent.abort ⇒ propagate(child.abort)                    # 부모가 죽으면 자식도 죽음
assert SubagentStart fired ⇒ SubagentStop fired eventually      # 생명주기 종료 보장
assert verification_worker ≠ implementation_worker              # 검증과 구현 역할 분리
```

## 7.3 상태 격리는 자식 에이전트가 오염을 최소화해야 함을 의미합니다

포크된 에이전트의 두 번째 핵심은 `createSubagentContext()`입니다. 소스 코드에서 기본 동작은 매우 명확합니다. 기본적으로 모든 가변 상태는 격리되어 부모를 방해하지 않도록 합니다.

기본적으로 수행하는 작업은 다음과 같습니다.

- `readFileState` 우선 복제(clone)
- 직접 공유하는 대신 자식 컨트롤러(child controller) 생성
- `getAppState`를 래핑하여 자식 에이전트가 권한 승인 프롬프트(permission prompt)를 피하도록 함
- `setAppState`는 기본적으로 아무 작업도 하지 않음(no-op)
- `nestedMemoryAttachmentTriggers`, `loadedNestedMemoryPaths` 등의 집합 재구성

`shareSetAppState`, `shareSetResponseLength`, `shareAbortController`와 같이 명시적으로 동의(opt-in)한 경우에만 특정 콜백을 공유합니다.

이 설계는 멀티 에이전트를 구축할 때 많은 사람이 간과하는 사실을 드러내기에 매우 중요합니다. 자식 에이전트의 가장 귀중한 점은 자신의 국소적 혼란이 메인 스레드를 오염시키지 않도록 방지할 수 있다는 것입니다. 연구 중의 오판, 임시로 읽은 파일 상태, 일회성 추론의 가지, 진행 중인 도구 결정 등을 모두 메인 컨텍스트에 직접 기록하면 결국 더 빠른 속도로 오염된 결과물만 얻게 됩니다.

Claude Code의 태도는 명확합니다. 공유는 명시적 합의에 기반해야 하며, 격리가 기본 윤리입니다. 이 윤리는 대화형 장난감이 아닌 데이터베이스 트랜잭션 설계와 비슷합니다. "우리는 모두 한 팀이니 상태를 마음대로 공유해도 된다"고 가정하지 않고, "가변 상태는 반드시 우선 격리하고, 공유할 부분만 나중에 결정한다"고 가정합니다.

## 7.4 코디네이터(coordinator) 모드는 합성(synthesis)이 희소한 능력임을 보여줍니다

`src/coordinator/coordinatorMode.ts`만 보면 Claude Code가 코디네이터에게 요구하는 바가 매우 절제되어 있음을 알 수 있습니다. 코디네이터의 역할은 다음과 같습니다.

- 사용자의 목표 달성 지원
- 워커(worker)에게 연구, 구현, 검증 지시
- 결과 종합 및 사용자와 소통
- 직접 답변 가능한 질문은 직접 처리하고, 무분별한 위임 방지

5절 프롬프트의 가장 핵심적인 문구는 **Always synthesize(항상 합성하십시오)**입니다. 워커가 연구 결과를 보고하면, 코디네이터는 이를 완전히 이해한 뒤 구체적인 프롬프트를 작성해야 합니다. "연구 결과에 기반하여(based on your findings)"와 같은 표현을 쓰거나 이해 과정을 다시 워커에게 외주 주어서는 안 됩니다.

이 문구는 멀티 에이전트의 핵심입니다. 진정으로 희소한 능력은 병렬 출력이 아니라, 워커의 국소적 지식을 다시 명확하고 실행 가능하며 검증 가능한 다음 단계로 압축하는 것입니다. 이 계층이 부족하면 멀티 에이전트는 곧 예의 바른 과업 전달 기계로 전락합니다. Claude Code는 프롬프트 설계에서 연구와 합성을 분리하고 코디네이터가 결과에 책임을 지도록 요구합니다. 후속 프롬프트에는 반드시 구체적인 파일, 위치, 변경 사항이 포함되어야 합니다. 연구는 분산될 수 있지만, 이해는 다시 수렴되어야 합니다.

## 7.5 검증은 반드시 독립적인 단계여야 합니다. 그렇지 않으면 "구현 완료"가 "문제 해결"을 사칭하게 됩니다

`coordinatorMode.ts`에는 꼭 기록해둘 만한 내용이 있습니다. 일반적인 과업을 다음 단계로 나눕니다.

- 연구(Research)
- 합성(Synthesis)
- 구현(Implementation)
- 검증(Verification)

그리고 검증의 목표는 단순히 코드가 존재함을 확인하는 것이 아니라 코드가 유효함을 증명하는 것임을 강조합니다. 소스 코드에는 거의 무정할 정도로 다음과 같이 명시되어 있습니다.

- 기능이 활성화된 상태에서 테스트 실행
- 오류를 관련 없는 것으로 치부하지 말고 조사
- 회의적인 태도 유지
- 독립적으로 테스트하고 도장 찍듯 승인하지 말 것

이는 Claude Code가 검증을 구현 워커가 부수적으로 수행하는 작업이 아니라, 제2의 품질 관문으로 취급함을 의미합니다. 프롬프트는 구현에 대한 자기 검증과 독립적인 QA(품질 보증)로서의 검증을 명확히 분리합니다.

왜 중요할까요? "코드를 수정했다"는 사실과 "그로 인해 코드가 올바르다"는 사실 사이에는 넓은 강이 있으며, 모델은 특히 그 위에 종이 다리를 놓는 데 능숙합니다. 변경 사항, 설명, 그럴듯한 테스트 출력은 모두 실제 기능이 시스템에서 제대로 작동함을 보장하지 않습니다. 검증을 별도로 분리하는 이유는 "코드를 수정할 수 있다"는 능력이 "결과물을 납품할 수 있다"는 사실을 사칭하는 것을 막기 위함입니다. 구현은 수정에 집중하고, 검증은 수정 사항이 살아남을 자격이 있는지 의심하는 역할을 합니다.

## 7.6 훅(hook)과 과업 생명주기는 서브에이전트가 일회용이 아님을 보여줍니다

멀티 에이전트 시스템에서 간과하기 쉬운 또 다른 지점은 시작(spawn)만큼이나 종료(cleanup)가 중요하다는 점입니다.

`src/utils/hooks/hooksConfigManager.ts`는 `SubagentStart`와 `SubagentStop` 두 가지 훅을 정의합니다. 전자는 서브에이전트 시작 시 트리거되며 `agent_id`와 `agent_type`을 입력받습니다. 후자는 종료 직전 트리거되며 `agent_transcript_path`를 포함하고, 종료 코드 2를 통해 stderr를 서브에이전트로 피드백하여 계속 실행하게 할 수도 있습니다.

이는 Claude Code에서 서브에이전트가 생명주기 노드가 명시적으로 노출된 시스템 객체임을 의미합니다. 시작 시 관찰 가능하고, 종료 전 개입할 수 있으며, 기록 경로는 추적 가능합니다. 여기서 핵심은 "서브에이전트 종료" 또한 관리되어야 하는 이벤트라는 점입니다.

동시에 `src/tasks/LocalAgentTask/LocalAgentTask.tsx`의 `registerAsyncAgent()`는 또 다른 측면을 보여줍니다. 각 비동기 에이전트는 정리 핸들러(cleanup handler)를 등록하며, 부모 에이전트가 중단되면 자동으로 자식 중단 컨트롤러로 전파됩니다. 과업 종료 후에는 출력물 배제(evict), 상태 업데이트, 정리 등록 해제 등이 수행됩니다.

이 메커니즘은 대화형 패널이 아닌 운영체제와 매우 유사합니다. 핵심 관심사는 다음과 같습니다.

- 이 에이전트가 여전히 실행 중인가
- 부모 과업이 죽었을 때 자식도 함께 죽어야 하는가
- 출력 파일은 계속 유지되어야 하는가
- 정리 콜백이 누수되지 않았는가

![Claude Code 멀티 에이전트 런타임 생명주기](diagrams/diag-ch07-01-multi-agent-lifecycle.png)

많은 멀티 에이전트 데모는 "새 에이전트를 하나 더 띄울 수 있다"는 수준에서 그치지만, Claude Code는 최소한 한 걸음 더 나아갔습니다. 에이전트를 리소스를 누수하거나, 상태를 잔류시키거나, 부모 프로세스 종료 후 고아가 될 수 있는 실행 객체로 간주합니다. 이것이야말로 에이전트를 시스템 구성 요소로 다루는 방식입니다.

### 서브에이전트 생명주기 실패 행렬 (failure matrix)

| 이벤트 순서 | 이전 상태 | 트리거 | 다음 단계 | 임계값 |
|---|---|---|---|---|
| 부모 중단 + 자식 실행 중 | 자식 미완료 | 부모 중단 | 자식 중단 전파, 정리 대기 | 고아 프로세스 허용 안 됨 |
| 자식 비정상 종료 | 자식 비정상 종료 | `SubagentStop` 종료코드 ≠ 0 | 출력물 배제, 종료 훅 실행 | 종료코드 2는 stderr 피드백 허용 |
| 자식 시간 초과 | 자식 과도한 실행 | `registerAsyncAgent` 시간 초과 | 자식 중단, 합성 결과 기록 | — |
| 캐시 키 편차 | `CacheSafeParams` 변경됨 | 포크(fork) | 포크 거부 또는 캐시 재계산 | 반드시 완전히 일치해야 함 |
| 공유 상태 미선언 | opt-in 미활성화 | 자식의 `setAppState` 쓰기 시도 | 무동작(no-op), 부모 오염 방지 | 기본 격리 |
| 메모리 충돌 | 메모리가 현상과 불일치 | 구 기록 읽기 | 현상 신뢰, 메모리 갱신/삭제 | 검증 선행 필수 |
| 정리 누수 | 핸들러 미취소 상태 과업 종료 | 최종 정리(finalize) | 강제 등록 해제 + 배제 | 연결된 핸들러 잔류 불가 |

## 7.7 검증은 코드뿐만 아니라 기억과 제안에도 적용됩니다

멀티 에이전트와 검증은 코드 변경 이후에만 발생하는 것이 아닙니다. Claude Code는 메모리 시스템에도 매우 주의 깊은 원칙을 심어두었습니다.

`src/memdir/memoryTypes.ts`는 메모리 기록이 구식이 될 수 있음을 명시합니다. 메모리에 기반하여 사용자에게 제안하기 전에 현재 상태를 검증해야 하며, 기억이 현재 현실과 충돌하면 현재 관찰된 상태를 신뢰하여 구식 메모리를 갱신하거나 삭제해야 합니다.

이 문장은 멀티 에이전트 장에서 시간 편차와 컨텍스트 편차에 저항하는 시스템의 기본적인 습관을 잘 보여줍니다. 시스템이 새로 작성된 코드만 검증하고 구식 메모리, 가설, 색인을 검증하지 않는다면 과거 정보에 의해 엉뚱한 방향으로 유도될 것입니다.

이런 관점에서 검증은 스킬(skill)이자 조직적 기강입니다. 과업을 위임하고, 정보를 저장하고, 다른 에이전트가 먼저 실행되게 할 수는 있지만, 사용자가 그에 따라 행동하기 전에는 항상 누군가 현재의 현실로 돌아와 그 내용이 여전히 사실인지 재확인해야 합니다.

## 7.8 멀티 에이전트는 불확실성을 분할함으로써 문제를 해결합니다

Claude Code의 멀티 에이전트 설계는 불확실성을 분할한다는 단순한 목표를 중심으로 합니다. 연구 워커는 국소적 컨텍스트에서 탐색하고, 구현 워커는 수정에 집중하며, 검증 워커는 회의적인 태도를 전문으로 하고, 코디네이터는 중간에서 수렴하여 사용자와 소통합니다.

이러한 분할의 가장 큰 장점은 책임이 명확하고 오류 지점을 특정할 수 있다는 것입니다. 연구에서 단서를 놓쳤는지, 합성이 내용을 제대로 이해하지 못했는지, 구현에서 오류를 범했는지, 검증이 소홀했는지를 모두 지목할 수 있습니다. 반면, 하나의 거대한 덩어리처럼 작동하는 단일 에이전트 방식은 문제가 발생하면 전체를 수정해야 합니다. 멀티 에이전트의 진정한 가치는 병렬 처리가 아니라 서로 다른 종류의 불확실성을 서로 다른 컨테이너에 가두고, 코디네이터가 이를 재조직화하는 데 있습니다.

## 7.9 소스 코드에서 추출할 수 있는 7번째 원칙

이 장을 한 문장으로 요약하면 다음과 같습니다.

> 멀티 에이전트 시스템은 명확한 분업에 의존합니다. 연구, 구현, 검증, 그리고 합성이 각각 다른 제약 컨테이너 안에 존재하고, 마지막에 코디네이터가 결과를 다시 결합하여 납품 가능한 결과물로 만들어야 합니다.

Claude Code 소스 코드는 이 판단을 다음과 같이 뒷받침합니다.

- `forkedAgent.ts`: 캐시 안전 매개변수, 사용량 추적, 상태 격리를 우선하여 포크를 런타임 제어 문제로 다룸
- `createSubagentContext()`: 가변 상태를 기본 격리하고 명시적 동의(opt-in)를 통해서만 공유 허용
- `coordinatorMode.ts`: 연구 결과를 전달하는 대신 합성(synthesis)을 요구하여 이해 과정을 외주 주지 않음
- 검증과 구현의 독립적 분리: 검증이 구현과 해제되어야 함을 명시
- `hooksConfigManager.ts`: `SubagentStart`/`SubagentStop` 생명주기 훅을 통해 서브에이전트 관찰 가능
- `LocalAgentTask.tsx`: 부모 중단 전파, 정리, 출력 배제를 처리하여 에이전트 생명주기 관리 보장

엔지니어링 원칙으로 정리하자면 다음과 같습니다. 캐시와 상태 경계를 먼저 고려하고 그 다음에 인격 분업을 논하십시오. 자식 에이전트는 기본적으로 격리하고 공유는 명시적으로 선언하십시오. 연구는 위임할 수 있으나 종합은 외주 줄 수 없습니다. 검증은 반드시 구현과 분리되어야 하며, 그렇지 않으면 시스템은 자기 증명적인 정확성만을 강화하게 됩니다. 에이전트 생명주기는 관찰 가능하고, 중단 가능하며, 정리 가능해야 합니다. 병렬 처리의 진정한 가치는 속도가 아니라 더 명확한 책임 분담에 있습니다.

다음 장에서는 이 메커니즘을 팀에 도입할 때, 개인의 기술을 어떻게 조직의 제도로 바꿀지 다룹니다. 즉, `CLAUDE.md`, 스킬(skill), 승인(approval), 훅(hook), 메모리(memory) 등을 어떻게 "고수가 개인적으로 사용하는 도구"에서 "팀이 안정적으로 재사용 가능한 엔지니어링 실천"으로 전환할 것인가를 논합니다.
