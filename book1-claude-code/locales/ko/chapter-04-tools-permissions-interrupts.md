# 4장 도구, 권한과 인터럽트: 왜 에이전트는 세계를 직접 만지면 안 되는가

## 4.1 모델이 도구를 호출하기 시작하면, 문제의 성격이 변합니다

텍스트만 출력하는 모델은 오류가 발생해도 주로 의사소통 비용을 증가시킬 뿐입니다. 일단 도구 호출을 시작하면 문제의 성격이 바뀝니다. 도구는 의견이 아니라 동작이며, 동작은 현실 세계와 접촉합니다. 모델이 설명을 잘못 작성하면 영향은 이해의 영역에 머물지만, 실행해서는 안 될 명령어를 실행하면 파일이 삭제되고, 프로세스가 중단되며, Git 이력이 엉망이 될 수 있습니다. 능력의 향상은 결과의 강력함을 동반합니다.

따라서 도구 시스템에서 가장 중요한 문제는 단 하나입니다. 누가 이 도구들을 제어할 것인가? Claude Code의 대답은 도구를 관리형 실행 인터페이스(managed execution interface)로 변환하여, 모델이 직접 세계를 만지지 못하도록 하는 것입니다.

## 4.2 도구 스케줄링은 행동 헌법의 일부입니다

Claude Code는 `src/services/tools/toolOrchestration.ts:19`의 `runTools()`에서 매우 대표적인 작업을 수행합니다. 일련의 `tool_use`를 직접 실행하지 않고, 먼저 동시성 안전(concurrency safety)에 따라 배치(batch)로 나눕니다.

`src/services/tools/toolOrchestration.ts:91`의 `partitionToolCalls()`에서 시스템은 먼저 도구의 `inputSchema`를 읽은 다음, `isConcurrencySafe()`를 호출하여 해당 유형의 호출이 병렬 실행에 적합한지 판단합니다. 적합하면 병렬 배치에 포함하고, 적합하지 않으면 직렬 단위로 분할합니다.

이것은 성능 최적화처럼 보이지만, 실제로는 일관성 설계에 더 가깝습니다. 도구 시스템이 일단 병렬 처리를 허용하면, 반드시 답변해야 할 오래된 문제가 있습니다. 컨텍스트 변경을 누가 결정하고 어떤 순서로 적용할 것인가? Claude Code는 병렬 경로에서 가장 먼저 완료된 도구가 컨텍스트를 선점하게 두지 않고, `toolOrchestration.ts:31`에서 `:63`까지 `contextModifier`를 캐시한 후, 원래의 블록(block) 순서대로 재생(replay)합니다. 즉, 실행은 병렬일지라도 의미론적인 컨텍스트 진화는 결정론적 순서를 유지합니다.

이것은 전형적인 엔지니어링 보수주의입니다. 전제는 이렇습니다. 병렬 처리는 처리량(throughput)을 향상시킬 수 있지만, 인과 관계의 질서를 파괴해서는 안 됩니다. 도구가 컨텍스트 일관성을 보장하지 못한 채 속도만 높인다면, 시스템에 또 다른 종류의 무작위성을 만들어낼 뿐입니다.

성숙한 에이전트 시스템은 병렬 처리를 맹신하지 않습니다. 병렬 처리를 기본값으로 자유롭게 두는 것이 아니라, 스스로 무해함을 증명해야 하는 예외로 취급합니다. Claude Code는 여기서 문제의 확산 속도를 충분히 고려하고 있습니다.

## 4.3 도구를 실행하기 전, 이미 많은 일이 일어납니다

많은 사람이 `tool_use`가 나타나면 다음 단계는 자연스럽게 실행이라고 생각합니다. Claude Code의 구현은 진정으로 신뢰할 수 있는 시스템은 그렇게 경솔하지 않음을 보여줍니다.

`src/services/tools/toolExecution.ts:30` 이후, `runToolUse()`가 의존하는 실행 로직은 이미 권한(permission), 훅(hooks), 원격 측정(telemetry), 합성 오류 구체화(synthetic error materialization)와 같은 기능들을 연결해 두었습니다. 세부 사항을 일일이 추적하지 않더라도 전체 구조를 보면 알 수 있습니다. Claude Code에서 도구 실행은 다음과 같은 전체 프로세스를 포함하는 완전한 흐름입니다.

- 사전 검증(pre-check)
- 실행 중 이벤트(in-flight events)
- 실행 후 수정(post-execution correction)
- 실패 보상(failure compensation)

이는 여기서 도구의 위상이 일반적인 라이브러리 함수와 다르다는 것을 의미합니다. 라이브러리 함수는 기본적으로 프로그램 내부에 속하며 호출자가 결과를 감당하지만, 도구는 모델과 외부 세계 사이의 인터페이스에 속하므로 시스템은 호출자가 안정적인 판단력을 갖추었다고 가정할 수 없습니다. 다시 말해, 도구 실행 주변에 이렇게 많은 포장층이 필요한 이유는 호출자 자체가 가장 불안정한 변수이기 때문입니다.

설계 철학상 이 점은 매우 중요합니다. 도구는 "모델 능력의 연장선"으로 모델링해서는 안 되며, "런타임이 위험을 대신 관리해야 하는 외부 기능"으로 모델링해야 합니다. 일단 이 점을 받아들이면 권한, 훅, 인터럽트(interrupt), 합성 결과(synthetic result)와 같은 구조들은 부담이 아니라 상식처럼 느껴집니다.

## 4.4 권한은 능력보다 우선합니다: Claude Code는 모델에게 자연스러운 권한이 있다고 보지 않습니다

Claude Code의 권한 진입점은 `src/hooks/useCanUseTool.tsx:27` 이후입니다. `CanUseToolFn`의 존재 자체가 한 가지 사실을 설명합니다. 도구 실행 허용 여부는 모델 자신이 결정하는 것이 아니라, 권한 판정 체인(permission decision chain)에 맡겨야 한다는 것입니다.

`useCanUseTool()`에서 시스템은 모델이 도구 요청을 제안했다고 해서 기본적으로 실행하지 않습니다. 대신, 먼저 `hasPermissionsToUseTool(...)`을 호출하여 권한을 판단합니다(`useCanUseTool.tsx:37` 참조). 반환 결과는 `allow`, `deny`, `ask`로 나뉩니다. 이것은 평범해 보이지만 실제로는 매우 중요합니다. 진정으로 성숙한 권한 시스템은 "할 수 있다"와 "할 수 없다" 외에도 시스템 스스로가 사용자를 대신해 결정을 내려서는 안 된다는 제3의 상태를 인정해야 하기 때문입니다.

`useCanUseTool.tsx:64` 이후, 이 체인은 다시 다른 경로로 나뉩니다.

- `deny`: 즉시 거부
- `ask`: 코디네이터(coordinator), 스웜 워커(swarm worker), 분류기(classifier) 또는 대화형 승인 경로로 진입
- `allow`: 비로소 실행 허용

이는 Claude Code가 구조적으로 위험한 생각을 부정하고 있음을 의미합니다. 즉, 모델이 사용자 의도를 이해했다고 해서 사용자 대신 실행할 권한이 있다는 생각입니다. 사실은 그렇지 않습니다. 의도를 이해하는 것은 권한을 갖는 것과 같지 않으며, 지속적인 권한을 갖는 것은 더더욱 아닙니다. 시스템은 반드시 "할 수 있는 것"과 "해도 되는 것"을 분리해야 합니다.

이 관점에서 권한 시스템은 에이전트의 역할을 명확히 하는 것입니다. Claude Code는 모델이 동작을 제안하는 것은 허용하지만, 실행 여부는 런타임, 규칙, 사용자가 결정합니다. 시스템은 의도적으로 능력 판단과 권한 판단을 분리합니다.

### 뼈대: 권한 판정 체인 (skeleton)

```
// skeleton: useCanUseTool()  (src/hooks/useCanUseTool.tsx:27)
decision = hasPermissionsToUseTool(tool, input, ctx)
match decision:
    case allow:  return exec(tool, input)
    case deny:   return reject(reason)
    case ask:    return route_to(coordinator | swarm_worker | classifier | interactive_prompt)

assert decision ∈ {allow, deny, ask}                    # 3상태, 불리언으로 편하게 처리 불가
assert ask never auto-escalates to allow                # 권한 없이 등급 상승 불가
assert deny is sticky for this tool_use_id              # 동일한 요청은 allow로 재시도 불가
```

## 4.5 권한 결과 자체가 일종의 런타임 의미론입니다

`src/utils/permissions/PermissionResult.ts:23` 이후, 시스템은 권한 동작을 위해 `allow`, `deny`, `ask`와 같은 전용 기술 함수까지 준비해 두었습니다. 이 세부 사항은 중요합니다. 이것은 Claude Code에서 권한이 단순한 내부 불리언 값이 아니라, 독립적인 의미론을 가진 런타임 객체임을 나타냅니다.

이 점이 중요한 이유는 권한 시스템이 시스템으로 하여금 "왜 이 단계가 진행되지 않았는가"를 명확하게 표현할 수 있게 해야 하기 때문입니다. 에이전트가 "확인이 필요합니다"라고 말할 때, 시스템은 책임의 경계를 선언하는 것입니다. 책임의 경계가 명확해지면 이후의 거부, 허용, 캐시 규칙, 임시 권한, 영구 권한 등이 자리 잡을 곳이 생깁니다.

더 직접적으로 말하자면, 에이전트 시스템이 "이 단계는 내가 할 수 있는 일인가, 할 수 없는 일인가, 아니면 물어봐야 하는 일인가"라는 차이조차 설명할 수 없다면 터미널을 건드려서는 안 됩니다. 터미널은 시스템을 대신해 의미론을 보완해주지 않으며, 오직 실행만 할 뿐이기 때문입니다.

## 4.6 StreamingToolExecutor는 인터럽트가 일등 시민 의미론임을 보여줍니다

도구가 일단 병렬 처리와 스트리밍(streaming) 실행을 시작하면, 인터럽트 문제는 즉시 복잡해집니다. 이때 시스템은 단일 동작이 아닌 queued(대기 중), executing(실행 중), completed(완료됨), yielded(양보됨) 등 여러 상태를 포함하는 큐(queue)를 마주하게 됩니다.

Claude Code는 `src/services/tools/StreamingToolExecutor.ts:34` 이후, 이 모든 것을 독립적인 스트리밍 도구 실행기로 명확하게 구현했습니다. 여기서 가장 주목할 점은 인터럽트와 폐기를 처리하는 방식입니다.

`StreamingToolExecutor.ts:64`에서 `:70` 사이에서 시스템은 스트리밍 fallback 시 현재 도구 세트를 전체적으로 discard(폐기)할 수 있도록 허용합니다. `:153`에서 `:205` 사이에서는 다음과 같은 이유를 포함하여 합성 오류 메시지(synthetic error message)를 생성합니다.

- sibling error(형제 오류)
- user interrupted(사용자 중단)
- streaming fallback(스트리밍 대체)

`:210` 이후에는 인터럽트 원인을 구체적으로 판단하여 다음을 구분합니다.

- 다른 병렬 도구의 오류로 인한 취소
- 사용자 인터럽트로 인한 취소
- fallback으로 인한 현재 배치(batch) 포기

더 자세히 보면 `:233` 이후 도구에는 `interruptBehavior`가 있어, 사용자가 대화에 끼어들 때 `cancel`할지 아니면 `block`할지 결정합니다.

이 설계는 큰 의미를 갖습니다. 이는 Claude Code가 인터럽트를 '실행 실패의 특수한 경우'로 이해하는 것이 아니라, 실행 자체와 마찬가지로 중요한 의미론으로 취급함을 보여줍니다. 시스템은 도구가 시작할 수 있는지 알아야 할 뿐만 아니라, 중단되었을 때 어떻게 마무리할지, 결과를 어떻게 보완할지, 새로운 메시지 삽입을 허용할지 등을 알아야 합니다.

이것이 바로 하네스 엔지니어링(harness engineering)의 기본적인 특징입니다. 시작을 설계할 뿐만 아니라 멈추는 법도 설계합니다. 멈추는 의미론이 없는 실행 시스템은 결국 사용자의 외부 인터럽트에 의존하여 설계를 보완할 수밖에 없습니다.

### 동시 처리와 인터럽트의 실패 순서 행렬 (failure matrix)

| 이벤트 순서 | 사전 상태 | 트리거 | 다음 단계 |
|---|---|---|---|
| 배치 내 단일 도구 실패 | 형제 도구 executing 상태 | sibling error | 다른 도구는 평소대로; 블록 순서대로 contextModifier 재실행 |
| 사용자 개입 + `interruptBehavior=cancel` | 도구 완료 전 | user interrupt | 실행 취소, `user interrupted` 합성 결과 생성 |
| 사용자 개입 + `interruptBehavior=block` | 도구 완료 전 | user interrupt | 도구를 자연스러운 끝까지 실행, 새로운 메시지 차단 |
| 스트리밍 fallback | 배치 queued/executing 상태 | fallback | 전체 배치 폐기, 순서대로 fallback 합성 결과 yield |
| abort 시 pending `tool_use` 존재 | 임의 | abort signal | 합성 `tool_result` 보완, 실행 원장(execution ledger) 닫기 |
| Bash 복합 명령이 서브커맨드 상한 초과 | 분류기 거부 | safety check | `deny`, ask 경로 진입 불가 |

## 4.7 왜 Bash는 영원히 다른 도구보다 더 의심스러운가

Claude Code의 도구 세계에서 Bash는 일반 도구가 아니라 위험 증폭기에 가깝습니다. 이유는 간단합니다. Bash는 지나치게 범용적이기 때문입니다. 인터페이스가 범용적일수록 도메인 지식만으로 제한하기가 더 어렵습니다. 파일 읽기 도구는 최소한 실수로 프로세스를 죽이지 않으며, grep 도구는 최소한 몰래 코드를 push하지 않지만, Bash는 거의 무엇이든 할 수 있습니다.

Claude Code의 Bash에 대한 불신은 매우 확실하게 작성되었습니다.

첫 번째는 프롬프트 단계로, `src/tools/BashTool/prompt.ts:42` 이후를 참조하십시오. 여기에는 git, PR, 위험 명령, 훅, force push, 대화형 플래그 등에 대한 다수의 명확한 규칙이 작성되어 있습니다. 해당 프롬프트는 장황해 보이지만 실제로는 매우 신중합니다. 결과가 큰 영역일수록 시스템은 장황함을 두려워하지 않습니다.

두 번째는 권한 및 보안 판정 단계입니다. `src/tools/BashTool/bashPermissions.ts:1` 이후 전체 구간에서는 셸 의미론, 명령어 접두사, 리다이렉션, 래퍼, 안전 환경 변수, 분류기와 규칙 매칭 등을 처리합니다. `bashPermissions.ts:95` 이후를 보면 복합 명령으로 인한 제어 상실을 방지하기 위해 서브커맨드(subcommand) 수에 제한까지 둔 것을 볼 수 있습니다.

이는 Claude Code에서 Bash가 특수한 검토가 필요한 위험 통로로 취급되며, 일반적인 명령 입구가 아님을 의미합니다. 엔지니어는 여기서 "Bash는 매우 강력하므로 특수 사례로 다루어야 한다"는 단순한 사실을 인정합니다.

이것은 참고할 만한 판단입니다. 고위험 능력은 범용적인 능력과 같은 대우를 받아서는 안 됩니다. 능력이 범용적일수록 더욱 특별하게 관리해야 합니다. Bash를 일반 도구로 취급하는 것은 대개 설계상의 게으름일 뿐입니다.

## 4.8 도구 시스템이 진정으로 보호하는 것은 사용자가 아니라 시스템 자신입니다

권한, 스케줄링, 인터럽트는 사용자를 보호하는 것처럼 보이지만, 사실 동시에 시스템 자신을 보호하고 있습니다. 에이전트 시스템이 불완전한 `tool_result`, 순서가 뒤섞인 컨텍스트 수정, 경계 없는 병렬 처리 부작용, 설명할 수 없는 인터럽트 의미론과 같은 문제를 남겨두도록 허용한다면, 가장 먼저 붕괴하는 것은 시스템의 일관성이기 때문입니다.

이 점은 `query.ts`와 도구 실행 계층에서 서로 맞물려 있습니다. 이전 장에서 언급했듯이 query loop는 인터럽트 시 합성 `tool_result`를 보완하며, 이번 장에서 볼 수 있듯이 StreamingToolExecutor도 내부적으로 discarded, hasErrored, siblingAbortController, interruptBehavior 등의 메커니즘을 예약해 두었습니다. 양쪽이 함께 작용하여 시스템이 "무엇을 실행했고, 무엇을 완료하지 못했으며, 왜 멈췄는지"라는 질문에 인과 관계를 추적할 수 있도록 합니다.

이것이 하네스의 핵심 의미 중 하나입니다. 시스템의 질서를 유지하는 것입니다. 많은 제약 조건은 표면적으로는 오작동을 방지하는 것처럼 보이지만, 더 깊은 층위에서는 시스템 자체가 설명할 수 없는 상태 파편으로 붕괴하는 것을 방지합니다.

## 4.9 소스 코드에서 추출할 수 있는 네 번째 원칙

이 장의 마지막은 한 문장으로 압축할 수 있습니다.

> 도구는 관리형 실행 인터페이스이며, 권한은 에이전트 시스템의 기본 기관입니다.

Claude Code의 소스 코드는 여러 지점에서 이 판단을 뒷받침합니다.

- `toolOrchestration.ts`는 도구를 먼저 배치하고 실행하므로, 스케줄링이 충동(impulse)보다 앞섭니다.
- `toolExecution.ts`는 도구 실행 주위에 훅, 권한, 원격 측정 및 합성 오류를 감싸므로, 실행은 단순 호출이 아닙니다.
- `useCanUseTool.tsx`는 권한 결과를 `allow / deny / ask`로 나누어 권한 부여를 독립적인 의미론으로 취급합니다.
- `StreamingToolExecutor.ts`는 인터럽트, fallback, 병렬 처리 오류를 위해 전용 의미론을 예약해 두어, 멈추는 것이 시작하는 것만큼 중요함을 보여줍니다.
- `BashTool/prompt.ts`와 `bashPermissions.ts`는 Bash에 대해 특수한 고강도 관리를 적용하여, 고위험 능력은 더욱 밀도 높은 제약을 수용해야 함을 입증합니다.

엔지니어링 원칙으로 요약하자면 다음과 같습니다. 모델이 제안하는 것이 권한을 가진다는 뜻은 아닙니다. 병렬 처리 시에는 인과 질서를 유지해야 합니다. 인터럽트는 일반적인 예외가 아닌 일등 시민 의미론이어야 합니다. Bash와 같은 고위험 도구는 특수 사례로 관리해야 합니다. 도구 시스템은 사용자와 런타임 자체를 모두 보호합니다.

다음 장에서는 이 시스템에서 흔히 발생하는 또 다른 착각인 "컨텍스트는 많을수록 좋다"는 주제를 다룹니다. Claude Code의 구현은 정반대의 사실을 보여줍니다. 진정으로 경험 많은 시스템은 컨텍스트를 창고로 사용하지 않고 리소스로 사용합니다. 이어지는 내용은 메모리, `CLAUDE.md`와 압축(compaction)이 어떻게 결합하여 컨텍스트 거버넌스 체제를 구성하는지에 관한 것입니다.
