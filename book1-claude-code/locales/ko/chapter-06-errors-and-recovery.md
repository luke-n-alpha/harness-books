# 6장 오류와 복구: 오류 발생 후에도 계속해서 작동하는 에이전트 시스템

## 6.1 공학 세계에서 가장 믿을 수 없는 말은 "정상적인 상황에서"입니다

많은 설계 문서가 "정상적인 상황에서"만을 다루며, 마치 주 경로(main path)가 완벽하면 오류가 알아서 사라질 것처럼 묘사합니다. 에이전트 시스템이 실제 운영 환경에 진입하면 이런 방식은 금방 밑천을 드러냅니다. 모델이 절단되고, 요청이 너무 길어지며, 훅(hook)이 루프를 만들고, 도구(tool)는 중단되며, 폴백(fallback)이 발생하고, 복구 로직 자체도 실패합니다.

에이전트 시스템의 성숙도는 시스템이 원활하게 작동할 때 얼마나 사람처럼 보이는지가 아니라, 고장이 났을 때 얼마나 시스템답게 행동하는지로 판단해야 합니다. Claude Code는 이 점에서 자신이 오류를 일으키지 않을 것이라고 가장하지 않습니다. 소스 코드에는 냉철한 판단이 반복적으로 반영되어 있습니다. 즉, 오류는 주 경로의 일부이며, 복구는 사전에 설계되어야 하는 런타임(runtime) 메커니즘이라는 점입니다.

## 6.2 `prompt too long`은 우연이 아닌 주기적인 현상입니다

긴 세션을 다루는 에이전트에게 `prompt too long`은 언젠가 반드시 찾아오는 계절 변화와 같습니다. 이를 우발적인 예외로 취급한다면 시스템은 결국 그 대가를 치르게 될 것입니다.

Claude Code의 `query.ts`는 이를 우발적인 예외로 처리하지 않습니다. `src/query.ts`에서 시스템은 이러한 오류를 즉시 사용자에게 그대로 노출하지 않고 "일시적으로 보류"합니다. 스트리밍 단계에서 `withheld`(보류) 로직은 다음과 같은 복구 가능한 오류를 식별합니다.

- prompt too long
- media size error
- max output tokens

이것이 의미하는 바는 명확합니다. 일부 오류는 복구 시스템이 먼저 처리하도록 전달한 뒤 사용자에게 노출할지 결정해야 한다는 것입니다. 이 순서가 중요한 이유는, 사용자에게는 원시 오류 유형보다 시스템이 계속해서 작업을 수행할 수 있는지 여부가 더 중요하기 때문입니다.

`prompt too long` 분기에서 Claude Code는 먼저 더 저렴하고 보수적인 복구 경로를 시도합니다. 컨텍스트 압축(context compaction)이 활성화되어 있다면 `recoverFromOverflow()`를 호출하여 이미 스테이징(staged)된 압축을 먼저 처리합니다. 그래도 해결되지 않으면 `reactiveCompact.tryReactiveCompact()`로 진입합니다. 즉, 복구는 계층화되어 있습니다. 먼저 알려진 누적을 비우고, 그 다음에 더 무거운 전체 텍스트 압축을 수행하며, 처음부터 시스템을 재구축하지는 않습니다.

이런 순서에는 공학적인 감각이 뚜렷합니다. 진정으로 훌륭한 복구 시스템은 모든 오류를 '가장 무거운 망치'로 내려치지 않습니다. 먼저 가장 세밀한 컨텍스트를 보존하려고 시도하고, 필요할 때만 더 거친 요약으로 대체합니다.

## 6.3 반응형 압축이 말해주는 것: 복구의 핵심은 스스로를 죽음의 루프로 몰지 않는 것입니다

많은 시스템이 복구를 수행할 때 저지르는 흔하면서도 어리석은 실수가 있습니다. 오류가 복구 가능하다고 판단하는 순간, 오류가 우발적인 사건에서 자원 재난으로 격상될 때까지 멈추지 않고 계속 재시도하는 것입니다.

Claude Code는 이 점을 매우 경계합니다. `query.ts`의 두 곳에서 이러한 경계심을 확인할 수 있습니다.

첫 번째는 `hasAttemptedReactiveCompact`입니다. 반응형 압축을 이미 시도했다면, 같은 종류의 문제가 다시 발생했을 때 시스템은 무분별하게 다시 시도하지 않습니다. 엔지니어들은 압축 후에도 여전히 해결되지 않는다면, 다시 압축을 시도하는 것은 같은 실패를 다른 방식으로 반복할 뿐이라는 사실을 잘 알고 있기 때문입니다.

두 번째는 정지 훅(stop hooks)의 무한 루프 방지 처리입니다. 소스 코드에는 매우 직설적인 주석이 달려 있습니다. `prompt too long` 이후에도 정지 훅이 개입하게 두면 '죽음의 소용돌이(death spiral)'가 발생할 수 있는데, 경로는 대략 다음과 같습니다.

오류 → 훅 차단 → 재시도 → 오류 → 훅 차단

이 문구는 문학적이지 않지만, 그 어떤 문학보다 정직합니다. 시스템에서 가장 위험한 오류는 실패 분기와 복구 분기가 서로 물고 늘어지며 무한히 스스로를 복제하는 경우임을 인정하고 있기 때문입니다.

그래서 Claude Code는 `prompt too long`을 복구할 수 없을 때, 오류를 직접 노출하고 정지 훅을 건너뜁니다. 이유는 간단합니다. 이 상황에서 형식적인 절차를 계속 진행하는 것은 나쁜 상황을 더 의례적으로 만드는 것뿐이기 때문입니다.

## 6.4 `max_output_tokens` 처리: 복구는 이어쓰기를 중심으로 합니다

대규모 언어 모델(Large Language Model, LLM) 제품에는 좋지 않은 습관이 하나 있습니다. 출력이 절단되면 먼저 정중한 사과부터 합니다. "죄송합니다, 방금 절단되었습니다. 요약해 드릴게요." 태도는 좋아 보이지만 실제로는 작업에 거의 도움이 되지 않습니다.

`src/query.ts:1185` 이후의 Claude Code 처리는 공학 시스템에 훨씬 더 가깝습니다. 시스템은 먼저 비용이 낮은 복구를 시도합니다. 현재 더 보수적인 상한(cap)을 사용하고 있다면, `maxOutputTokensOverride`를 더 높은 값으로 올려 동일한 요청을 즉시 재실행합니다. 주목할 점은, 이 단계에서 메타 메시지를 삽입하지도 않고, 모델에게 먼저 인사말을 하게 하지도 않으며, 시스템이 모델에게 원래 작업을 완료할 기회를 먼저 제공한다는 것입니다.

더 높은 상한으로도 충분하지 않으면 두 번째 복구 계층으로 진입합니다. 모델에게 메타 사용자 메시지를 추가하는데, 그 내용은 매우 실질적입니다. 대의는 다음과 같습니다.

직접 계속하세요. 사과하지 마세요. 요약하지 마세요. 절단된 곳이 문장의 중간이라면 그 부분부터 계속 쓰세요. 남은 작업은 더 작게 나누세요.

이것은 매우 교훈적인 시스템 지시입니다. Claude Code가 복구를 이해하는 방식은 추가 토큰을 예의 바른 마무리에 쓰지 않고 작업의 연속성을 최대한 유지하는 것임을 보여줍니다. 긴 작업에서 이러한 차이는 매우 큽니다. 매번 절단 후 요약할 때마다 예산이 추가로 소모되고, 의미적 표류(semantic drift)가 증가하기 때문입니다. 결국 시스템은 작업 자체를 수행하기보다 자신이 수행한 작업을 계속 검토하는 일을 하게 됩니다.

따라서 `max_output_tokens`의 경우, 더 나은 복구는 보통 이어쓰기입니다. Claude Code는 이 지점에서 정중한 설명을 우선하기보다 작업의 연속성을 명확히 보장합니다.

## 6.5 자동 압축의 서킷 브레이커: 복구 시스템도 통제가 필요합니다

앞의 섹션들이 "단일 오류를 어떻게 복구할 것인가"를 다룬다면, `src/services/compact/autoCompact.ts`가 다루는 것은 다른 계층의 문제입니다. 복구 메커니즘 자체가 계속해서 실패할 때는 어떻게 해야 하는가 하는 점입니다.

소스 코드의 답변은 간단하면서도 정확합니다. 끝없이 재시도하지 마세요.

`AutoCompactTrackingState`는 `consecutiveFailures`를 추적합니다. 실패 횟수가 임계값을 초과하면, `shouldAutoCompact`가 "압축이 필요하다"고 판단하더라도 시스템은 압축을 건너뜁니다. 소스 코드의 주석은 과거의 사례를 언급합니다. 연속된 자동 압축 실패로 인해 대량의 API 호출이 낭비되는 세션들이 있었기 때문에 서킷 브레이커가 필수가 되었다는 것입니다.

서킷 브레이커의 본질은 현재의 복구 방법이 이 상황에서 이미 효과를 잃었다는 것을 인정하는 것입니다. 성숙한 시스템은 성공할 때만 지표를 기록해서는 안 되며, 반복된 실패 속에서 언제 손을 떼야 하는지 알아야 합니다. 손을 놓지 못하는 복구 시스템은 브레이크가 없는 자동차와 다를 바 없습니다.

하네스 엔지니어링(harness engineering) 관점에서 보면, 여기서 추출할 수 있는 원칙은 단단합니다. 모든 자동 복구 메커니즘은 반드시 계수 가능하고, 횟수 제한이 가능하며, 차단 가능해야 합니다. 그렇지 않으면 복구가 보험으로부터 새로운 화재의 시작점으로 변질됩니다.

### 서킷 브레이커 불변식(invariants)

```
assert withheld_error ∈ {prompt_too_long, media_size, max_output_tokens}  # 복구 가능한 집합이 명확함
assert hasAttemptedReactiveCompact ⇒ skip further reactive compact        # 자기 루프 없음
assert consecutiveFailures < MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES          # 브레이커가 작동 중
assert compact aborted by user ⇏ summary_success                           # 중단 ≠ 성공
assert every withheld recoverable_error surfaces iff recovery exhausted    # 보류된 오류는 반드시 출구가 있음
```

### 복구 경로 실패 매트릭스

| 이벤트 순서 | 선행 상태 | 트리거 | 다음 단계 | 임계값 |
|---|---|---|---|---|
| PTL → collapse | `stagedCollapse > 0` | `prompt_too_long` | `recoverFromOverflow()` | — |
| PTL → compact | `stagedCollapse = 0` | `prompt_too_long` | `tryReactiveCompact()` | 회차당 한 번 |
| PTL → surface | `hasAttemptedReactiveCompact` | `prompt_too_long` | 직접 노출; 정지 훅 건너뛰기 | — |
| compact PTL | 압축 입력 과다 | 내부 `prompt_too_long` | `truncateHeadForPTLRetry()` | 초기 API 라운드를 묶음 단위로 삭제 |
| MOT → cap↑ | cap < MAX | `max_output_tokens` | `maxOutputTokensOverride` 상향 | cap ∈ {보수적, 최대} |
| MOT → 계속 | cap = MAX | `max_output_tokens` | 메타 사용자 메시지 추가, 이어쓰기 | 요약 없음, 사과 없음 |
| autocompact 연속 실패 | `consecutiveFailures` ≥ 임계값 | 다음 트리거 | 압축 건너뛰기, 직접 노출 | `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3` |
| 사용자 중단 | 스트리밍 중 대기 중인 `tool_use` | Esc | 나머지 결과 소비 + 합성 `tool_result` | 원장 반드시 결산 |

## 6.6 압축 자체도 실패합니다. 그래서 "수정 동작"도 수정 전략이 필요합니다

`compactConversation()` 코드에는 매우 현실적인 순간이 있습니다. 바로 압축 요청 자체도 `prompt too long`에 걸릴 수 있다는 것을 인정한다는 점입니다.

이것은 검은색 유머를 담고 있습니다. 시스템이 컨텍스트를 줄이기 위해 요약 요청을 보내는데, 그 요약 요청마저 컨텍스트가 너무 길어서 실패하는 것입니다. 많은 설계들이 이런 상황을 숨기려고 하는 이유는, 너무 직접적으로 역설을 드러내기 때문입니다. 그러나 공학 시스템이 먼저 해결해야 하는 것은 계속 작동하는 것이지, 표면의 완전성을 유지하는 것이 아닙니다.

Claude Code의 처리 방식은 `compact.ts`에서 `truncateHeadForPTLRetry()`를 도입하는 것입니다. 압축 입력이 너무 길 때, 시스템은 먼저 더 이른 API 라운드들을 머리 부분부터 묶음 단위로 제거한 뒤 압축을 재시도하여, 사용자가 "압축도 압축할 수 없는" 상태에서 갇히는 것을 방지합니다.

트레이드오프는 명확합니다. 이 대체 경로는 손실이 발생하고 이력을 잃을 수 있지만, 사용자가 완전히 교착 상태에 빠지지 않도록 우선하는 것입니다. 소스 코드의 주석은 이를 '최후의 탈출 해치(last-resort escape hatch)'라고 설명합니다.

이러한 선택이 가지는 가치는 현실의 제약을 외면하지 않는다는 점입니다. 시스템이 질식할 위기에 처했을 때, 우선순위는 먼저 호흡을 회복하는 것이고, 그 다음이 정보의 높은 충실도를 유지하는 것입니다.

## 6.7 중단 의미론: 인터럽트도 복구의 일부입니다

많은 팀이 중단을 사용자 경험으로만 분류하고, 오류 복구 논의에 넣으려 하지 않습니다. 런타임 관점에서, 인터럽트는 의미론적 종료가 필요한 실패 상태입니다.

Claude Code는 두 계층에서 이를 처리합니다. `query.ts`에서는 스트리밍 중단 시 `StreamingToolExecutor.getRemainingResults()`를 소비하여 발급되었지만 아직 완료되지 않은 도구 호출에 대해 합성된 도구 결과를 생성함으로써, 매달린 약속을 방지합니다. `compact.ts`에서는 중단 컨트롤러(abort controller)를 포크된 에이전트에 전달하고 `APIUserAbortError`를 명시적으로 처리하여, "사용자가 Esc로 중단한 압축"이 성공적인 요약으로 집계되지 않도록 방지합니다.

중단은 단순히 "사용자가 읽기를 멈춤"이 아니라 올바른 종료를 필요로 하는 상태 전환입니다. 예외만 처리하고 중단을 무시하는 복구는 의미론적으로 반은 깨진 실행 자취를 많이 남겨 두게 됩니다.

## 6.8 오류 처리가 진정으로 보호하는 것: 실행 내러티브의 일관성

Claude Code의 복구 철학에는 종종 간과되는 목표가 하나 있습니다. 바로 실행의 내러티브 일관성을 보호하는 것입니다. 즉, 시스템이 여전히 자신이 시도한 것이 무엇인지, 왜 실패했는지, 어떤 복구 경로를 사용했는지, 지금 계속하는 중인지 / 중단하는 중인지 / 다시 경로를 틀고 있는 중인지를 명확히 설명할 수 있는지 하는 것입니다.

`query.ts`의 `transition.reason`, `maxOutputTokensRecoveryCount`, `hasAttemptedReactiveCompact`, 압축 경계, 그리고 합성된 오류 메시지들은 모두 이 내러티브를 깨지지 않도록 방지하는 반(反)기억상실 메커니즘입니다. 내러티브 일관성이 없으면, 시스템은 계속 텍스트를 출력하면서도 내부적으로는 분해됩니다. 사용자는 채우기용 텍스트를 보고, 운영팀은 훅 재시도와 압축 재시도가 복잡하게 얽혀 인과관계를 파악할 수 없으며, 팀은 시스템이 정말로 무엇을 겪었는지 더 이상 설명할 수 없게 됩니다. 오류 복구가 수정하는 것은 오류뿐만 아니라 시스템의 자기 설명 능력입니다. 설명 능력이 끊어지면, 공학의 대상은 불투명한 마법으로 격하됩니다.

## 6.9 소스 코드에서 추출할 수 있는 여섯 번째 원칙

이 장을 압축하면 한 문장으로 수렴됩니다.

> 에이전트 시스템의 신뢰성은 오류 발생 후에도 설명 가능하고, 범위 제한이 가능하며, 계속 실행 가능한 실행 질서를 유지할 수 있는지로 측정됩니다.

Claude Code의 소스 코드는 여러 핵심 지점에서 이 판단을 뒷받침합니다.

- `query.ts`는 복구 가능한 오류를 일시적으로 보류하여 분기 수준의 변환 후 노출합니다.
- prompt-too-long 복구는 컨텍스트 드레인을 먼저 거친 후 반응형 압축을 수행하며, 비용과 파괴성 순서로 정렬됩니다.
- `hasAttemptedReactiveCompact`와 정지 훅 가드는 복구의 자기 루프를 명확히 방지합니다.
- `max_output_tokens` 처리는 상한을 먼저 올린 후 정중한 요약보다 직접 계속하기를 선호합니다.
- `autoCompact.ts`의 연속 실패와 서킷 브레이커는 자동 복구가 반드시 계수 가능하고 차단 가능해야 함을 강제합니다.
- `compact.ts`는 압축 자체의 prompt-too-long 실패에 대한 강등 복구까지 포함합니다.

공학 원칙으로 추출하면: 복구를 계층화하되 한 개의 무거운 망치를 사용하지 말 것; 복구 로직은 자기 루프를 방지해야 할 것; 자동 복구는 계수 가능하고 차단 가능해야 할 것; 절단 후에는 요약보다 이어쓰기를 우선할 것; 중단도 의미론적 종료를 필요로 하는 실패 상태일 것; 신뢰성은 결국 오류 후에도 시스템이 자신의 행동을 설명할 수 있는지로 증명됩니다.

다음 장에서는 더 까다로운 문제 종류로 진입합니다. 바로 멀티 에이전트(multi-agent)와 검증(verification)입니다. 시스템이 더 이상 "자신이 출오류를 자신이 복구"하는 것을 넘어 작업을 다른 에이전트에게 위임하고 그 결과를 다시 검증하기 시작하면, 오류와 복구의 문제는 단일 스레드의 질서에서 조직 문제로 격상됩니다. 그때 당신이 마주하는 것은 단 하나의 모델이 실수할 수도 있다는 것이 아니라, 불안정한 실행 주체들이 어떻게 서로를 제약하는지 하는 문제가 됩니다.
