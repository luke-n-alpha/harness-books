# 서문: 하네스(harness), 터미널, 그리고 엔지니어링 제약

지난 몇 년간 사람들은 코드를 작성하는 모델을 에이전트(agent)라고 부르는 것을 좋아합니다. 이 단어는 명백히 낙관적인 색채를 띠고 있어서, 마치 모델이 저장소를 읽고, 도구를 호출하고, 괜찮은 수준의 패치를 생성할 수만 있다면 엔지니어링 환경에서 독립적으로 행동할 수 있을 것 같은 느낌을 줍니다. 하지만 엔지니어링 환경에는 분명한 결과가 따릅니다. 터미널, 파일 시스템, 그리고 Git 히스토리는 추상적인 공간이 아니며, 어떠한 변경 사항이라도 남긴 흔적은 사라지지 않습니다.

텍스트만 출력하는 모델은 오류가 발생했을 때 주로 이해하는 데 드는 비용을 발생시킵니다. 하지만 명령어를 실행하고, 파일을 작성하고, 네트워크에 접근하며, 저장소를 수정할 수 있는 모델은 오류 발생 후 실행 결과를 남깁니다. 디렉토리는 변경되고, 프로세스는 중단되며, 설정은 손상되고, 히스토리는 추적하기 어려워집니다. 이 단계에 이르면 핵심 문제는 모델이 충분히 똑똑한지가 아니라, 시스템이 충분한 제약을 제공하고 있는지가 됩니다.

이 책에서 다루는 내용이 바로 이러한 제약입니다.

저는 이것을 하네스 엔지니어링(harness engineering)이라고 부릅니다. 여기서 하네스(harness)는 엔지니어링 환경에서 모델의 행동 경계를 제한하기 위해 지속적으로 작동하는 제어 구조(control structure)의 집합으로 이해할 수 있습니다. 인공지능(Artificial Intelligence, AI) 코딩 에이전트(AI coding agent)에게 제약이 없는 능력은 사고의 피해 범위를 넓힐 뿐입니다.

이 책은 Claude Code 소스 코드에 대한 해설서가 아닙니다. 소스 코드는 물론 중요하지만, 디렉토리를 따라가며 하나씩 설명하다 보면 자칫 주석 모음집이 되기 십상입니다. 그런 내용은 함수가 무엇을 하는지는 설명할 수 있어도, 왜 시스템이 현재와 같은 구조로 나타나야만 하는지에 대한 답은 되지 못합니다. Claude Code와 같은 시스템을 이해하기 위해 `queryLoop()`, `compactConversation()`, `runTools()`가 존재한다는 것을 아는 것만으로는 충분하지 않습니다. 더 중요한 질문은 이것입니다. 왜 "코드를 작성할 수 있는" 시스템이 궁극적으로 프롬프트(prompt) 계층화, 권한(permission) 판단, 상태 기계(state machine), 압축(compaction), 복구(recovery) 분기, 서브에이전트(subagent) 생명주기, 검증(verification) 단계, 그리고 팀 제도와 같은 구조들을 필요로 하는 것일까요?

답은 간단합니다. 모델 자체가 불안정하기 때문입니다.

이 판단은 듣기 좋지 않을 수 있지만, 엔지니어링 시스템은 낙관적인 서사에 의존하여 유지될 수 없습니다. 구성 요소가 본질적으로 불안정하다면 시스템은 반드시 그 사실을 중심으로 설계되어야 합니다. 그렇지 않으면 문제는 사고 복구 과정에서 집중적으로 나타날 뿐입니다.

Claude Code는 구현 과정에서 명확한 공학적 절제를 유지하고 있기 때문에 연구할 가치가 있습니다.

- 모델이 계속해서 올바르게 작동할 것이라고 가정하지 않으므로, 질의 루프(query loop)를 사용하여 상태를 관리합니다.
- 도구 호출이 본질적으로 안전하다고 가정하지 않으므로, 권한과 스케줄링을 통해 도구를 제약합니다.
- 컨텍스트(context)가 많을수록 항상 좋다고 가정하지 않으므로, 메모리(memory), `CLAUDE.md`, 압축, 세션 메모리를 도입합니다.
- 오류를 우발적인 사건으로 보지 않으므로, 프롬프트가 너무 길 때, 최대 출력 토큰(max output tokens) 제한, 인터럽트(interrupt), 훅(hook) 루프가 발생할 때를 위한 복구 경로를 설계합니다.
- 멀티 에이전트(multi-agent)를 곧바로 더 강력한 능력과 동일시하지 않으므로, 시스템이 스스로를 보증하는 것을 피하기 위해 합성(synthesis)과 검증을 분리합니다.

이 모든 것들이 합쳐져야 비로소 에이전트가 됩니다. 모델은 에이전트를 구성하는 부품 중 가장 말을 잘하지만 가장 불안정한 부품일 뿐입니다.

그래서 이 책은 다음과 같은 변함없는 기본 입장을 고수합니다.

> 프롬프트는 에이전트가 어떻게 말할지를 결정하고, 하네스는 에이전트가 어떻게 행동할지를 결정합니다.

여기서 말하는 하네스는 부수적인 도구 계층이나 모델 능력에 대한 감정적인 방어책이 아닙니다. 하네스는 모델이 엔지니어링 환경에 진입하기 위한 전제 조건입니다. 이러한 제약이 결여되면 위험은 결국 사용자, 팀, 그리고 미래의 유지보수 담당자에게 전가됩니다.

여기서 한 가지 경계를 명확히 하겠습니다. 이 책에는 Claude Code 소스 코드가 포함되어 있지 않으며, 소스 코드를 길게 옮겨 적지도 않을 것입니다. 이유는 간단합니다. 저작권 경계 때문입니다. 우리가 할 수 있는 일은 합리적인 인용과 엔지니어링 분석의 범위 내에서, 소스 코드 구조를 바탕으로 설계 원칙, 운영 메커니즘 및 방법론적 판단을 추출하는 것이지, 저작권의 보호를 받는 구현 텍스트를 재배포하는 것이 아닙니다.

이 책은 두 가지를 수행하고자 합니다.

첫째는 Claude Code 소스 코드를 기반으로 시스템의 신뢰성을 실질적으로 결정하는 구조를 명확히 설명하는 것입니다. 컨텍스트 거버넌스(context governance)가 왜 주 경로(primary path)가 되어야 하는지, 왜 멀티 에이전트가 책임 분할 문제를 해결하는지, 왜 팀 제도가 생명주기 노드(checkpoint)에 포함되어야 하는지를 설명하는 데 중점을 둡니다. 단순히 "여기에 압축이 있다", "여기에 서브에이전트가 있다", "여기에 훅이 있다"고 나열하는 것이 아닙니다.

둘째는 이러한 구현 이면의 판단을 더 일반적인 엔지니어링 원칙으로 추출하는 것입니다. 구체적인 코드 버전은 변하고, 함수 이름은 바뀌며, 제품 형태도 달라질 것입니다. 하지만 사람들이 여전히 불안정한 모델을 실제 워크플로우(workflow)에 통합하려고 시도하는 한, 특정 원칙들은 여전히 유효할 것입니다. 예를 들면 다음과 같습니다.

- 오류 경로도 주 경로로 간주하고 설계해야 합니다.
- 검증은 '완료(done)' 정의에 반드시 포함되어야 합니다.
- 권한은 시스템의 부속 기능이 아니라 시스템의 기관(organ)입니다.
- 컨텍스트는 쓰레기통이 아니라 자원입니다.
- 멀티 에이전트는 역할 분담에 의존해야 하며, 인해전술에 의존해서는 안 됩니다.
- 팀 제도는 개인의 기교보다 중요합니다.

이러한 판단들이 타당하다면 Claude Code는 참조 표본으로 삼기에 더 적합합니다. 이 책의 가치는 사람들에게 똑같은 명령줄 인터페이스(Command Line Interface, CLI)를 복제하도록 가르치는 것이 아니라, 실제 엔지니어링 환경에 직면한 AI 에이전트가 어떻게 더욱 엄격한 제약 구조로 나아가는지를 보여주는 데 있습니다.

더 직접적으로 말하자면, 이 책은 모델을 포장하여 "엔지니어 같은" 환상을 만들어내는 방법을 논하는 것이 아니라, 모델이 엔지니어 수준의 안정성을 갖추지 못한 상태에서도 어떻게 실행 가능한 엔지니어링 시스템을 구축할 것인가를 논합니다.

이러한 작업들은 대개 눈에 띄지 않습니다. 롤백(rollback), 승인(approval), 권한, 검증, 압축, 유령 프로세스(orphan process) 정리 등은 눈에 띄지 않지만, 시스템이 장기간 안정적으로 운영될 수 있는지는 대개 이러한 부분들에 달려 있습니다. "사람처럼 자연스러운" 에이전트 경험만을 지나치게 추구하면, 결과적으로 시스템은 사람의 실수 패턴을 닮아가면서도 그 결과에 대한 책임은 지지 못하는 상황에 빠지게 됩니다.

그렇다면 이제 제약에 대해 이야기해 봅시다.

다음 9개의 장에서는 이러한 하네스 구조가 어떻게 형성되는지, 왜 반드시 이러한 방식으로 구성되어야 하는지, 그리고 팀이 개인의 경험을 재사용 가능한 엔지니어링 제도로 어떻게 축적할 수 있는지에 대해 논의합니다.
