# 8장 팀 도입: 똑똑한 도구를 지속 가능한 워크플로로 만들기

## 8.1 전문가의 성공이 곧 팀의 안전한 재사용으로 이어지지는 않습니다

많은 AI 코딩 도구는 숙련된 사용자의 손에서 인상적으로 작동합니다. 노련한 사용자는 언제 컨텍스트(context)를 보충해야 할지, 언제 모델을 면밀히 지켜봐야 할지, 그리고 언제 "이 디렉터리는 건드리지 마"라는 말 한마디로 동작을 제어해야 할지 알고 있습니다. 이는 팀에 쉽게 착각을 불러일으킵니다. 파워 유저들이 도구를 능숙하게 다룬다면, 팀 전체로의 도입은 그저 모범 사례 몇 가지를 더 적는 일 정도로 생각하기 쉽습니다.

문제는 개인의 기법이 효과를 발휘하는 이유가 바로 지속적인 감독, 배경 지식, 그리고 상황 판단에 의존하기 때문이라는 점입니다. 팀이 이 도구를 도입하는 순간 가정은 달라집니다. 모든 팀원이 어떤 명령어가 위험한지, 어떤 메모리(memory)가 오래된(stale) 것인지, 어떤 스킬(skill)이 서브에이전트(subagent)를 fork 하는지, 어떤 단계에서 승인을 건너뛰어도 되고 어떤 단계에서는 반드시 확인해야 하는지 모두 알고 있다고 가정할 수 없습니다. 팀이 해결해야 할 진정한 문제는 전문가의 머릿속에만 머물던 질서를 평범한 기여자들도 별다른 영웅적 노력 없이 반복할 수 있는 워크플로로 바꾸는 것입니다.

Claude Code의 소스 코드가 유용한 이유는 전문가의 동작을 명시적으로 드러냈기 때문입니다. 명령어에는 로딩 계층이 있고, 권한(permission)에는 결정 지점이 있으며, 서브에이전트에는 격리 경계가 있고, 런타임(runtime)에는 수명 주기 훅(hook)이 노출되어 있습니다. 코딩 에이전트를 도입하는 것은 더 똑똑한 자동 완성 기능을 추가하는 동시에, 누가 어떤 경계 안에서 무엇을 할 수 있는지를 재정비하는 과정이기도 합니다.

## 8.2 팀 도입의 첫걸음은 최소한의 경계를 명확히 하는 것입니다

팀 도입을 첫날부터 대규모 거버넌스 프로젝트로 상상한다면 이 장을 가장 오해하기 쉽습니다. 현실에서 대부분의 팀은 훅(hook), 감사 체인(audit chain), 정교한 스킬 카탈로그로 시작하지 않습니다. 그들의 출발점은 보통 훨씬 작습니다.

- 어떤 작업 분류가 에이전트 참여를 허용할 것인가
- 어떤 변경 사항이 여전히 사람의 검토(review)를 거쳐야 하는가
- 작업 완료로 간주하기 위해 반드시 수행해야 할 최소한의 검증(verification)은 무엇인가
- 어떤 리소스는 절대 접근해서는 안 되는가

이것들은 기본적인 질문처럼 들리지만, 어떤 거창한 슬로건보다 더 중요합니다. 초기 단계에서 팀은 최소한의 제어 경계를 명확히 정의하는 것에서 가장 큰 이득을 얻습니다.

이 경계를 잘못 설정하면 이후의 모든 자동화 계층이 왜곡됩니다:

- 허용 범위를 모호하게 정의하면, 사람들이 자동화해서는 안 될 곳에 에이전트를 사용하게 됩니다.
- 검토 책임을 모호하게 정의하면, 문제가 생겼을 때 마지막으로 확인해야 할 사람이 누구인지 아무도 알 수 없게 됩니다.
- 검증 기준을 모호하게 정의하면, 시스템은 방 안에서 가장 낮은 기준을 만족하는 법만 배우게 됩니다.
- 금지 구역을 모호하게 정의하면, 효율성 향상이 곧 사고 반경 확대로 이어집니다.

따라서 현실적인 롤아웃(rollout) 순서는 다음과 같습니다:

1. 허용 가능한 사용 범위를 정의합니다.
2. 검토 및 검증 기대치를 정의합니다.
3. 그다음 반복적인 워크플로 중 어떤 것이 형식적인 재사용의 가치가 있는지 결정합니다.

에이전트 자체의 성능이 충분함에도 팀이 실패하는 이유는 종종 이 단계를 건너뛰었기 때문입니다.

### 팀 단계별 도입 체크리스트 (builder checklist)

```
- [ ] 1주 차: 계층화된 CLAUDE.md 적용 — 팀 / 개인 / 프로젝트 모두 검증 가능
- [ ] 1주 차: 공통 검증 정의 (lint / type / test 명령어를 CLAUDE.md에 작성)
- [ ] 1주 차: 금지 구역을 저장소 수준의 하드 제약으로 인코딩 (디렉터리, 위험한 명령어)
- [ ] 2주 차: 결과에 따른 승인 정책(approval policy) 단계별 적용 (허용 / 거부 / 요청), Bash는 별도 규칙 적용
- [ ] 2주 차: 초기 3개 이하의 스킬 배포, 각 스킬은 전제 조건 / 사후 조건 / 검증 가능한 산출물을 가짐
- [ ] 2주 차: "알려진 문제가 있는 상태로 완료"에 대한 명시적 정책 정의
- [ ] 3주 차: stop / post-tool-use 훅(hook) 적용, 트랜스크립트(transcript)와 작업 결과물 기록
- [ ] 3주 차: 월간 오래된 메모리 유지 관리 프로세스 적용
- [ ] 3주 차: 상위 수준의 감사 전, 기준 재현(Git diff / PR / CI)의 공백 없는 확인
진입 장치: 신규 인원이 전문가의 동행 없이 사용할 수 있을 때, 워크플로가 성숙한 것으로 간주합니다.
```

## 8.3 `CLAUDE.md`는 안정적이고 계층적이며 논쟁이 적을 때 가치가 있습니다

앞서 `claudemd.ts`의 계층적 로딩을 다룬 바 있습니다. 이는 팀 도입 단계에서도 중요하지만, 좀 더 절제된 방식으로 해석해야 합니다.

팀 수준의 `CLAUDE.md`는 안정적인 규칙을 담는 데 가장 적합합니다. 모든 절차적 세부 사항을 다 넣을 필요는 없습니다. 예시는 다음과 같습니다:

- 저장소 수준의 하드 제약(금지된 디렉터리나 위험한 명령어 분류 등)
- 공통 검증 기대치(반드시 실행해야 할 최소한의 확인 사항 등)
- 협업 규율(사용자가 요청하지 않은 변경 사항을 덮어쓰지 않기, 명시적 지시 없이 더러워진 작업 트리(dirty worktree)를 리셋하지 않기 등)
- 출력 규율(검토 보고 시 결과(findings)를 먼저 알리고 요약을 뒤에 배치하기 등)

자주 바뀌는 임시 프로세스, 소수의 작업에서만 사용되는 조작 세부 사항, 명령어·스킬·스크립트로 표현하는 것이 더 나은 단계들은 `CLAUDE.md`에 담기에 적합하지 않습니다. `CLAUDE.md`가 백과사전처럼 방대해지면 안정성과 신뢰성을 동시에 잃게 됩니다. 팀원들은 어떤 규칙이 현재 유효한지 몇 달 전의 잔재인지 알 수 없게 되고, 시스템은 오래된 규범을 현재의 법으로 취급하는 법을 배우게 됩니다.

따라서 이상적인 팀 `CLAUDE.md`는 단순히 "큰" 것이 아닙니다. 거의 논쟁할 필요가 없을 정도로 안정적이어야 합니다. 그것은 게시판이 아니라 기초가 되어야 합니다.

## 8.4 스킬 수보다 검증 정의가 먼저입니다

코딩 에이전트 도입에서 가장 흔한 실패 중 하나는 팀이 '완료'에 대한 공유된 정의를 갖지 못하는 것입니다.

어떤 이는 "돌아가면 된다"고 생각합니다. 어떤 이는 절반 정도 테스트하면 충분하다고 여깁니다. 어떤 이는 모델이 그럴듯하게 설명만 해도 받아들입니다. 그런 환경에서 가장 똑똑한 시스템조차 가장 낮은 기준을 만족하는 법만 배우게 됩니다.

Claude Code는 반복적으로 이러한 방심을 경계합니다. 앞서 코디네이터(coordinator) 모드가 검증(verification)을 독자적인 단계로 분리하는 것을 보았고, 검증 관련 지침은 파일 존재 여부 확인을 넘어 해당 변경 사항이 실제로 작동함을 증명하는 것에 초점을 맞춥니다.

스킬은 프로세스를 복제할 수 있지만, 검증 정의만이 품질을 복제할 수 있기 때문에 이는 팀에게 특히 중요합니다.

더 현실적인 팀의 접근 방식은 많은 스킬을 만들기 전에 다음 세 가지를 정의하는 것입니다:

- 어떤 작업 분류에 독립적인 검증이 필요한가
- 검증에는 테스트, 로컬 실행, 로그 확인, 사람의 승인 등 최소한 어떤 동작이 포함되어야 하는가
- 검증에 실패했을 때 "알려진 문제가 있는 상태로 완료"라고 표시할 수 있는가

이 내용이 불분명하면 이후의 모든 자동화는 모호함을 가속화할 뿐입니다. 반대로 일찍 명확해진다면, 스킬이 아주 적은 팀이라도 일관된 품질의 하한선을 유지할 수 있습니다.

따라서 더 내구성 있는 롤아웃 순서는 보통 다음과 같습니다:

- 검증 정의를 먼저 표준화합니다.
- 반복적인 워크플로를 스킬이나 명령어로 패키징합니다.
- 그다음 더 복잡한 자동화 오케스트레이션을 고려합니다.

## 8.5 스킬은 그 자체로 제도라기보다 워크플로 모듈로 이해하는 것이 좋습니다

팀이 처음 스킬을 설계할 때 두 가지 잘못된 모델로 빠지기 쉽습니다. 하나는 스킬을 "그저 긴 프롬프트(prompt) 템플릿"으로 보는 것이고, 다른 하나는 스킬을 제도적 장치로 지나치게 신성시하는 것입니다. 둘 다 틀렸습니다.

Claude Code는 스킬을 단순한 프롬프트 조각 이상으로 다룹니다. 스킬이 의도와 일치하면 Skill 도구(tool)를 반드시 호출해야 하며, 이미 로드된 스킬은 중복 로드되지 않아야 하고, 스킬은 자체적인 경계와 도구 집합을 가진 서브에이전트 컨텍스트에서 실행될 수 있습니다. 따라서 스킬은 최소한 실행 의미를 갖춘 워크플로 모듈입니다. 하지만 팀 운영에 있어서는 더 실용적인 이해를 유지해야 합니다. 스킬을 에이전트 형태로 조직 전체를 인코딩하려 하기보다, 먼저 "이 반복적인 워크플로를 어떻게 안정적으로 재사용할 것인가"를 해결하는 데 초점을 맞춰야 합니다.

스킬 설계 시 답변해야 할 질문은 다음과 같습니다. 이 스킬은 어떤 작업 분류를 지원하는가, 기본적으로 어떤 도구를 사용할 수 있는가, 직접 실행할 것인가 아니면 서브에이전트로 fork 할 것인가, 작업 완료 후 어떤 검증 가능한 결과물이 남아야 하는가. 이 질문에 답하지 못하면 스킬은 이름만 그럴듯하고 내용은 모호한, 아무도 실제 동작을 확신할 수 없는 "반자동 슬로건"으로 전락합니다.

## 8.6 승인은 위험에 따라 계층화할 때 가장 잘 작동합니다

Claude Code는 한 가지 구분을 계속해서 강조합니다. 무언가를 할 수 있는 것과 그것을 할 권한(permission)이 있는 것은 다르다는 점입니다. 개인은 임시로 권한을 부여할 수 있지만 팀은 그럴 수 없습니다. 에이전트가 파일을 쓰고, Git 상태를 변경하고, 네트워크나 외부 시스템에 접속하는 순간, 그 모든 단계는 책임의 영역을 이동시키는 것이기도 합니다.

팀은 종종 반대의 실수를 범합니다. 처음부터 매우 복잡한 승인 분류 체계를 설계하느라 도입 비용을 감당할 수 없게 되고, 결국 아무도 실행하지 않게 됩니다. 도구 이름에 따라 획일적으로 나누기보다 위험에 따라 계층화하는 것이 훨씬 현실적입니다. 읽기 / 나열하기 / 순수 분석은 위험이 낮고, 작업 공간 변경 및 쓰기 작업은 훨씬 높으며, Git push나 외부 네트워크 및 민감한 환경 접속은 더 높습니다. 팀이 관리해야 할 것은 도구의 이름이 아니라 복구 불가능성과 환경적 민감성입니다. 이런 경계가 명확해지면 자동화가 잘못된 곳에서 피해를 키울 가능성이 줄어듭니다.

### 승인 규칙 템플릿

```
// 템플릿: 승인 규칙 (useCanUseTool의 3값 결정과 유사)
rule {
    name:           <단명>
    match:          { tool, args_pattern, cwd_scope }
    risk_tier:      read | write | irreversible      // 도구 이름이 아닌 결과에 따른 계층화
    decision:       allow | deny | ask
    ask_to:         coordinator | reviewer | operator
    ttl:            session | turn | persistent
    audit:          transcript + PR comment + CI log
}
assert 모든 복구 불가능한 작업 ⇒ decision ∈ {deny, ask}    # 복구 불가능 작업은 반드시 차단
assert 복합 Bash 명령어 > subcommand_cap ⇒ deny        # 복합 명령어는 자동으로 방출하지 않음
assert ask는 결코 자동으로 allow로 확대되지 않음                     # 3값 결정은 붕괴하지 않음
```

## 8.7 훅은 강력하지만 일반적으로 롤아웃의 첫 단계는 아닙니다

`hooksConfigManager.ts`는 `SessionStart`, `SessionEnd`, `SubagentStart`, `SubagentStop`, `PreCompact`, `PostCompact`, `FileChanged`, `DirectoryChange` 등 많은 수명 주기 이벤트를 노출합니다. 이를 종합해 보면 훅의 진정한 가치가 명확해집니다. 바로 적절한 시점에 규칙이 작동하게 한다는 점입니다.

예시는 다음과 같습니다:

- 지침 파일이 로드될 때 조직 수준의 컨텍스트 주입
- 서브에이전트가 멈추기 전 검증 단계 실행
- 압축(compaction) 경계 전후로 요약 기록
- 세션 종료 시 아카이브 또는 정리 작업 수행

이 모든 것은 유용하지만, 유용하다고 해서 반드시 첫 번째 단계여야 하는 것은 아닙니다.

대부분의 일반적인 엔지니어링 팀에게 첫 움직임은 보통 더 단순합니다. 저장소 수준의 지침 파일, 코드 검토 규칙, CI 및 테스트 기대치, 소수의 반복적인 명령어 또는 스킬 세트가 그것입니다. 훅은 규모, 위험 수준, 또는 규제 준수 압박이 더 커질 때 성과를 냅니다. 그전에는 팀이 감당하기보다 관리해야 할 부분(유지되지 않는 스크립트, 불분명한 트리거 타이밍, 수동 단계보다 더 큰 디버깅 비용 등)만 늘어날 뿐입니다.

따라서 더 성숙한 결론은 훅이 고급 자동화 인터페이스라는 점입니다. 훅은 시간 경계가 있는 동작에 적합하며, 일반적으로 기반 거버넌스가 안정된 후에 도입해야 합니다.

## 8.8 재현 가능성은 중요하지만, 기준 추적과 고급 감사 기록은 분리해야 합니다

관측 가능성과 감사 가능성은 이 장에서 가장 과장되기 쉬운 부분입니다. 팀은 당연히 무슨 일이 일어났는지, 표류가 어디서 시작되었는지, 누가 결정적인 단계를 승인했는지 알고 싶어 합니다. Claude Code의 로그, 텔레메트리(telemetry), 작업 결과물, 트랜스크립트(transcript) 경로, 훅 이벤트, 에이전트 알림은 강력한 재현 가능성을 구축합니다.

하지만 두 계층은 구분해야 합니다. 기준 계층(Git diff 및 커밋 이력, PR 코멘트 및 검토자 결정, CI 및 테스트 로그, 이슈 트래커 및 승인 결론)은 대부분의 팀이 이미 가지고 있으며 일상적인 복원에 충분합니다. 고급 계층(트랜스크립트 경로, 도구 호출 기록, 훅 이벤트, 압축(compaction) 전후 요약, 서브에이전트 사용 및 상태 변화)은 규모나 규제 준수의 필요성이 정당화될 때 성과를 냅니다. 핵심은 계층 2에 투자하기 전에 계층 1의 공백을 없애는 것입니다. 많은 팀이 깔끔한 검토나 검증 기준이 없는 상태에서 에이전트 전체에 대한 감사 가능성을 너무 일찍 추구하다가, 거버넌스를 고비용의 전시 행정으로 만들곤 합니다.

따라서 기준 재현 가능성은 팀 도입의 필수 요건이며, 고급 감사 기록은 고위험/대규모/강한 규제 환경을 가진 팀을 위한 강화 요소입니다. 이러한 구분이 있어야 플랫폼 팀의 거버넌스를 모든 팀의 출발점으로 오인하는 일을 막을 수 있습니다.

## 8.9 소스 코드에서 추출할 수 있는 여덟 번째 원칙

이 장을 닫는 문장은 다음과 같은 형태일 때 더 정확합니다:

> 팀 도입은 허용 가능한 경계, 검증 기준, 반복적인 워크플로가 초기에 안정적으로 고정될 때 가장 효과적입니다.

Claude Code의 소스가 실제로 제안하는 바를 이식 가능한 형태로 옮기면 다음과 같습니다:

- 지침은 안정적인 규칙과 임시 프로세스 세부 사항이 뒤섞이지 않도록 계층화되어야 합니다.
- 스킬은 반복적인 워크플로에 유용하지만 적용 가능성, 도구 범위, 결과물이 명확할 때만 그렇습니다.
- 승인은 도구 이름에 따라 조잡하게 분류되기보다 위험 및 환경에 따라 계층화되어야 합니다.
- 훅은 강력하지만 기반 거버넌스가 안정된 후에 도입되어야 합니다.
- 재현 가능성은 계층적으로 구축되어야 합니다. 기준 추적성을 먼저 확보하고, 상황이 정당화될 때 고급 감사 가능성을 추가합니다.

팀이 실행 가능한 원칙으로 번역하면 다음과 같습니다: 대규모 롤아웃 전에 허용 가능한 사용 범위를 정의하고, 스킬 수를 늘리기 전에 검증 정의를 표준화하고, 훅과 오케스트레이션을 추가하기 전에 검토, CI, 최소한의 안정적인 지침 파일로 하한선을 설정하고, 처음부터 전체적인 무거운 감사를 요구하지 않으면서도 모든 자동화 경로를 설명 가능하게 만들어야 합니다. 목표는 제도를 쌓는 것이 아니라 경계를 명확히 하고 시스템을 견딜 수 있게 만드는 것입니다.

다음 장은 이 책을 마무리합니다. 앞선 장들을 관통하는 하나의 판단이 있습니다. 모델은 가장 불안정한 구성 요소이므로, 우리가 실제로 설계해야 할 것은 모델이 신뢰할 수 없을 때에도 주변 시스템을 견딜 수 있고, 검증 가능하며, 교정 가능하게 만드는 방법입니다.
