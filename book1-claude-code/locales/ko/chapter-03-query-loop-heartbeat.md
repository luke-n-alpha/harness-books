# 3장 질의 루프(query loop): 에이전트 시스템의 심장박동

## 3.1 에이전트 시스템의 성숙도를 판단하려면, 먼저 루프가 있는지 확인하십시오

코드를 작성하는 모델을 강화된 질의응답(Question and Answering, Q&A) 인터페이스로 간주하는 것은 가장 흔한 실수입니다. 시스템이 도구를 호출하고, 턴(turn)을 넘나들며 실행하고, 인터럽트(interrupt)를 처리하고, 상태를 저장하고, 컨텍스트(context)를 압축(compaction)하기 시작하면 '일문일답'은 더 이상 작동하지 않습니다. Claude Code는 구조적으로 에이전트가 지속적이고 상태가 있는(stateful) 실행 과정을 의존한다는 사실을 명확히 인정합니다.

`src/query.ts:219`의 `query()`는 껍데기에 불과하며, 진정으로 중요한 것은 `src/query.ts:241`의 `queryLoop()`입니다. 이는 반복 간 상태를 유지하며, 먼저 전처리를 통한 거버넌스를 수행한 뒤 스트리밍 단계로 진입합니다. 모델이 응답을 반환한 후에는 도구 실행, 복구(recovery), 압축, 다음 턴 진행 또는 종료 중 무엇을 할지 결정합니다.

![Claude Code Query Loop Core](diagrams/diag-ch03-01-query-loop-core.png)

핵심 용어는 라이프사이클(lifecycle)입니다. 시스템이 에이전트로 불릴 수 있는지는 말을 잘하는지가 아니라, 몇 턴이 지난 후에도 자신이 무엇을 하고 있는지 알고 있는지에 달려 있습니다.

## 3.2 상태는 주 업무의 일부입니다

많은 시스템이 설계 초기에 상태를 짐으로 여기며, 마치 상태가 없는(stateless) 것이 더 우아한 것처럼 경향을 보입니다. 에이전트 시스템의 경우 이러한 선호는 제한적인 효과만 있습니다. 실제 워크플로우에 진입하면 상태는 자연스럽게 나타나기 마련입니다. 상태를 무시한다고 해서 상태가 사라지지 않으며, 오히려 관리하기 더 어려운 방식으로 돌아올 뿐입니다.

Claude Code는 이에 대해 매우 직접적인 태도를 취합니다. `src/query.ts:203`부터 `:217`까지, 시스템은 질의 루프의 가변 상태를 다음과 같이 명확히 정의합니다.

- `messages`
- `toolUseContext`
- `autoCompactTracking`
- `maxOutputTokensRecoveryCount`
- `hasAttemptedReactiveCompact`
- `pendingToolUseSummary`
- `stopHookActive`
- `turnCount`
- `transition`

`src/query.ts:268`에 이르면, 이 상태들은 질의 루프가 시작될 때마다 하나의 `State` 객체로 전체적으로 조립되며, 이후 각 continue 분기에서 전체적으로 업데이트됩니다.

Claude Code는 복구, 압축, 예산, 훅(hook), 턴(turn) 카운트를 지역 변수에 흩뿌려 놓지 않고, 이들이 모여 "이번 턴이 끝난 후 다음 턴을 어떻게 계속할 것인가"의 기초가 됨을 인정합니다. 스크립트는 이 단계가 완료되었는지만 신경 쓰지만, 에이전트 시스템은 이번 단계가 실패한 이후에 다음 단계가 앞서 남겨진 상태를 받아 계속할 수 있는지도 고려해야 합니다.

### 골격: queryLoop()

```
// skeleton: queryLoop()  (src/query.ts:203–1305)
state = { messages, toolUseContext, autoCompactTracking,
          maxOutputTokensRecoveryCount, hasAttemptedReactiveCompact,
          pendingToolUseSummary, stopHookActive, turnCount, transition }

while not done(state):
    govern_input(state)                 // prefetch / snip / microcompact / collapse / autocompact
    events = stream_model(state)
    for e in events:
        if e.is(tool_use):  schedule(e, state.toolUseContext)
        if e.is(api_error): return surface(e)
    if interrupted:
        drain_tools_with_synthetic_results(state); break
    state = advance(state, recover_if_needed(state))

assert state.turnCount_{t+1} >= state.turnCount_t            # 상태의 단조성
assert every emitted tool_use has a matching tool_result     # 실행 원장의 폐쇄
assert hasAttemptedReactiveCompact ⇒ no further compact      # 자가 루프 방지
```

## 3.3 질의 루프의 첫 번째 책무는 입력 거버넌스입니다

외부에서 에이전트 시스템을 볼 때, 많은 사람은 그 핵심 동작이 "모델을 호출하는 것"이라고 생각하기 쉽습니다. 그러나 공학적으로는 모델 호출 전에 수행되는 긴 정리 작업이 훨씬 더 중요합니다. Claude Code는 `queryLoop()`에서 이 부분을 아주 명확하게 기술합니다.

모델 스트림에 본격적으로 진입하기 전에 시스템은 다음 작업을 수행합니다.

- 관련 메모리(memory) 프리패치 시작, `src/query.ts:297` 참조
- 스킬(skill) 발견(discovery) 프리패치, `src/query.ts:323` 참조
- 압축 경계(compact boundary) 이후 유효한 메시지 슬라이싱, `src/query.ts:365` 참조
- 도구 결과 예산(tool result budget) 적용, `src/query.ts:369` 참조
- 이력(history) 스닙(snip), `src/query.ts:396` 참조
- 마이크로 압축(microcompact) 수행, `src/query.ts:412` 참조
- 컨텍스트 붕괴(context collapse) 수행, `src/query.ts:428` 참조
- 마지막으로 자동 압축(autocompact) 시도, `src/query.ts:453` 참조

이 순서 그 자체가 하나의 아키텍처 선언입니다. 이는 독자에게 Claude Code가 "컨텍스트 거버넌스(context governance)"를 "모델 추론"보다 앞선 순위에 둔다는 점을 알려줍니다. 즉, 혼돈 속에서 질서를 정리하는 책임을 모델에 떠넘기지 않고, 런타임이 먼저 거버넌스를 완료한 뒤 더 깔끔해진 입력을 모델에 전달합니다.

이는 매우 중요한데, 많은 시스템이 이와 반대로 동작하기 때문입니다. 엄청난 양의 컨텍스트를 일단 집어넣고, 무엇이 중요하고 무엇이 중요하지 않은지 모델 스스로 판단하기를 기대합니다. 그러한 방식은 일견 쉬워 보이지만, 실제로는 런타임이 짊어져야 할 책임을 확률 분포에 떠넘기는 것에 불과합니다.

Claude Code의 방식은 전통적인 공학 절차에 가깝습니다. 먼저 현장을 정리하고, 그다음 실행을 시작합니다. 화려함을 추구하지는 않지만, 대개 더 안정적입니다.

## 3.4 모델 호출은 루프의 한 단락일 뿐, 루프 자체가 아닙니다

앞선 정리 작업이 모두 끝나면 Claude Code는 모델 호출 단계로 진입합니다. 이 단계는 `src/query.ts:652` 이후에 나타납니다. 여기서 특별히 짚고 넘어갈 세부 사항이 있는데, 시스템은 전체 결과가 돌아올 때까지 동기적으로 기다리는 것이 아니라 `for await`를 사용하여 모델 출력을 스트림으로 소비한다는 점입니다.

이는 Claude Code에서 모델 출력이 단순히 "최종 답변"이 아니라 하나의 이벤트 스트림임을 의미합니다. 이벤트에는 다음이 포함될 수 있습니다.

- 어시스턴트 텍스트
- `tool_use` 블록
- 사용량(usage) 업데이트
- 중단 사유(stop reason)
- API 오류

이는 `src/query.ts:826` 이후에서 더욱 분명해집니다. 시스템은 어시스턴트 메시지를 저장하고, 그 안에서 `tool_use` 블록을 추출하여 후속 조치(follow-up)가 필요한지 결정하며, 스트리밍 중에도 도구를 `StreamingToolExecutor`에 전달할 수 있습니다.

공학적 관점에서 이는 근본적인 변화입니다. 모델 출력을 이벤트 스트림으로 취급하게 되면, 시스템 아키텍처는 더 이상 단순한 "요청-응답"이 아니라 "구동-스케줄링-피드백"의 과정이 됩니다. 스트리밍의 의미는 단순히 글자 몇 개를 더 빨리 보는 것에 그치지 않고, 모델 출력이 완전히 끝나기도 전에 런타임이 다음 단계의 실행을 준비할 수 있도록 하는 데 있습니다.

이것이 바로 앞서 질의 루프야말로 에이전트 시스템의 심장박동이며, 모델 호출 자체가 아니라고 말한 이유입니다. 모델 호출은 심장박동 중 한 번의 수축일 뿐, 시스템을 유지하는 것은 입력이 어떻게 들어오고, 스트림이 어떻게 소비되며, 도구가 어떻게 스케줄링되고, 실패가 어떻게 복구되며, 언제 다음 턴을 계속할지 결정하는 전체 순환 과정입니다.

## 3.5 심장박동은 인터럽트를 처리해야 합니다. 그렇지 않으면 그것은 그저 관성일 뿐입니다

진정한 심장박동은 계속 뛰는 것뿐만 아니라, 필요할 때 멈출 수도 있어야 합니다. 멈추지 못한다면 시스템에는 관성만 남게 됩니다.

Claude Code의 인터럽트 처리 방식은 매우 실질적입니다. `src/query.ts:1011` 이후 시스템은 스트리밍 중단(streaming abort)을 최우선으로 처리합니다. `streamingToolExecutor`가 활성화되어 있다면, 이미 발행된 `tool_use`가 짝을 이루는 결과 없이 남지 않도록 잔여 결과를 소비하고 합성 도구 결과(synthetic tool_result)를 생성해야 합니다. 그렇지 않은 경우 `yieldMissingToolResultBlocks()`를 사용하여 인터럽트 기록을 능동적으로 보완합니다.

이 뒤에는 아주 기본적인 공학 원칙이 있습니다. 시스템이 외부로 특정 실행을 약속했다면, 인터럽트 시에도 원장(ledger)을 맞추어야 합니다. 사용자가 중간에 중단했다고 해서 앞선 몇 개의 `tool_use`가 일어나지 않은 척할 수는 없습니다. 외부 시스템, UI, 트랜스크립트는 일관된 인과 관계가 필요하며, 결과가 "중단됨"일지라도 중단은 완결성을 가져야 합니다.

이 작업이 중요한 이유는 에이전트 시스템이 다중 도구, 다중 턴 상태에 진입하면 외부 세계는 단순히 "최종 답변이 있는가"를 넘어 "그것이 남긴 궤적을 해석할 수 있는가"를 요구하기 때문입니다. 해석할 수 없는 실행 궤적은 언젠가 운영 문제, 감사(audit) 문제, 혹은 팀 내에서 아무도 설명할 수 없는 장기적인 시한폭탄이 됩니다.

따라서 인터럽트 처리는 런타임의 기본 책임입니다. 이미 시작된 동작은 "끝나지 않음"이라는 결론을 내리더라도 그에 대한 설명이 있어야 합니다.

## 3.6 심장박동은 또한 복구를 처리해야 합니다. 그렇지 않으면 취약한 반복 노동에 불과합니다

인터럽트가 외부 세계에서 가해지는 예상치 못한 충격이라면, 복구는 시스템 내부에 남겨둔 여유입니다. 복구 능력이 없는 루프는 겉보기에 얼마나 깔끔하든 결국 똑같은 문제를 드러냅니다. 바로 행운을 설계로 착각했다는 것입니다.

Claude Code의 복구 처리는 단순한 재시도(retry)가 아니라 층층이 쌓이는 방식입니다. 가장 대표적인 것은 `prompt-too-long`(프롬프트가 너무 김)과 `max-output-tokens`(최대 출력 토큰 제한)입니다.

`src/query.ts:1065` 이후 시스템은 마지막 어시스턴트 메시지가 보류(withheld)된 `prompt too long`인지 판단합니다. 그렇다면, 우선 컨텍스트 붕괴(context collapse)를 통해 적체된 항목을 제출하려 시도합니다(`:1086`에서 `:1116` 참조). 그것으로도 부족하다면 반응형 압축(reactive compact)으로 진입합니다(`:1119`에서 `:1166` 참조). 바꾸어 말하면, 시스템은 비용과 파괴적인 영향력이 낮은 순서부터 높은 순서로 단계적인 복구를 시도합니다.

`max_output_tokens`에 대한 처리도 마찬가지입니다. `src/query.ts:1185` 이후 시스템은 우선 토큰 제한(cap)을 높이는 것을 시도하며, 그것으로도 안 되면 메타 메시지를 생성하여 모델이 중단된 지점부터 내용을 계속 작성하도록 합니다. 먼저 사과하거나 요약하거나 아름다운 빈말을 작성하는 대신 말입니다.

이는 Claude Code의 설계 철학을 잘 보여줍니다. 복구를 모델 실패 후의 예의 바른 행동이 아닌, 런타임의 주 경로(main path) 일부로 간주합니다. 복구의 의의는 시스템에 계속 일할 기회를 주는 데 있습니다. 실제 공학 현장에서 계속해서 작업을 수행하는 것은 겉으로 예의를 차리는 것보다 보통 더 중요합니다.

## 3.7 종료 조건은 하나일 수 없습니다. 그렇지 않으면 시스템은 실패와 완료를 혼동하게 됩니다

일반적인 질의응답 시스템의 종료 조건은 비교적 단순합니다. 답변이 있으면 끝입니다. 에이전트 시스템은 이렇게 나태해서는 안 됩니다. 세션 내에서 "현재 턴 종료"가 곧 "작업 완료"를 의미하지 않으며, "시스템 성공"을 보장하지도 않기 때문입니다.

Claude Code의 질의 루프는 최소한 다음 상황들을 구분합니다.

- 스트리밍은 정상 완료되었으나 `tool_use`가 있어 후속 조치가 필요한 경우
- `tool_use`가 없어 스톱 훅(stop hooks) 및 잠재적 후속 판정으로 진입하는 경우
- 사용자에 의해 인터럽트된 경우
- `prompt-too-long` 복구가 트리거된 경우
- `max-output-tokens` 복구가 트리거된 경우
- 스톱 훅 차단으로 인해 루프에 재진입하는 경우
- API 오류로 즉시 반환하는 경우

이는 `src/query.ts:1062`부터 `:1305`까지 확인할 수 있습니다. 특히 `:1267`부터 `:1305`까지의 스톱 훅 부분은 훅을 처리할 뿐만 아니라 "압축 후에도 여전히 너무 길어 다시 훅에 차단되고, 다시 무한 압축되는" 데드 루프를 방지합니다.

이 부분은 매우 주목할 만합니다. 많은 시스템은 실패하면 재시도한다는 단순한 생각만 가집니다. 반면 Claude Code는 재시도 그 자체도 관리되어야 하는 행위임을 인정합니다. 시스템은 왜 재시도하는지, 무엇을 시도했는지, 어떤 보호 상태를 재설정하면 안 되는지, 어떤 상황이 무한 루프를 야기하는지 알아야 합니다. 바로 이러한 판단들이 "계속 시도하는" 시스템과 "언제 그만두어야 하는지 아는" 시스템을 구분 짓습니다.

### 종료 조건 행렬

| 이벤트 순서 | 이전 상태 | 트리거 | 다음 단계 |
|---|---|---|---|
| 스트림 정상 종료 + `tool_use` | 미완료 tool_use 존재 | 중단 사유(stop reason) | 후속 조치, 도구 실행 진입 |
| 스트림 정상 종료, `tool_use` 없음 | 대기 중인 도구 없음 | 중단 사유 | 스톱 훅 진입 |
| 사용자 인터럽트 | 임의 | 중단 신호 | 잔여 결과 소비, 합성 도구 결과 생성 |
| `prompt_too_long` | 압축 미시도 | 복구 가능한 오류 | 붕괴/반응형 압축 실행 |
| `max_output_tokens` | 제한(cap) 미도달 | 중단 사유 | `maxOutputTokensOverride` 상향, 재실행 |
| `max_output_tokens` | 제한 도달 | 중단 사유 | 메타 사용자 메시지 추가, 이어 쓰기 |
| 스톱 훅 차단 + PTL 재발 | `hasAttemptedReactiveCompact` | 이중 실패 | 스톱 훅 건너뜀, 오류 표면화 |
| API 오류 | — | API 오류 | 즉시 반환, 재시도 없음 |

## 3.8 QueryEngine은 이것이 세션 라이프사이클에 속함을 증명합니다

`queryLoop()`만으로도 충분하지 않다면, `QueryEngine`의 존재가 이를 더 직접적으로 설명해 줍니다.

`src/QueryEngine.ts:176`부터 소스코드는 명확히 밝힙니다.

> QueryEngine은 대화의 질의 라이프사이클과 세션 상태를 소유합니다.

![Claude Code QueryEngine Turn Flow](diagrams/diag-ch03-02-queryengine-turn-flow.png)

![Claude Code QueryEngine State Carry-Over](diagrams/diag-ch03-03-queryengine-state-carryover.png)

이 문장은 전체 장의 핵심을 명확히 전달합니다. `QueryEngine`은 한 번의 호출이 아닌 대화의 질의 라이프사이클을 관리합니다. `src/QueryEngine.ts:180`에서 소스코드는 하나의 `QueryEngine`이 하나의 대화에 대응하며, 매 `submitMessage()`마다 동일한 대화 내에서 새로운 턴이 시작되고 상태가 지속적으로 보존됨을 추가로 설명합니다.

`src/QueryEngine.ts:675` 이후 `QueryEngine`은 준비된 `messages`, `systemPrompt`, `userContext`, `systemContext`, `toolUseContext`를 `query()`에 전달한 뒤, 어시스턴트, 사용자, 압축 경계 메시지를 트랜스크립트에 다시 기록합니다.

이는 질의 루프가 대화 시스템의 진정한 실행 중심임을 의미합니다. 외부의 UI, SDK, 세션 영속성(session persistence)은 모두 이를 중심으로 돌아갑니다. Claude Code의 설계를 이해하려면 단순히 도구 목록을 보거나 프롬프트 텍스트만 읽어서는 안 되며, 궁극적으로는 이 루프가 어떻게 앞서 언급한 제약 조건을 연속적인 행동으로 실현하는지 살펴보아야 합니다.

## 3.9 소스코드에서 도출할 수 있는 세 번째 원칙

이 장은 마지막으로 다음과 같은 한 문장으로 수렴할 수 있습니다.

> 에이전트 시스템의 핵심 역량은 복구 가능한 실행 루프를 유지하는 것입니다.

앞선 절들의 골격, 불변성(invariants), 종료 조건 행렬은 이미 충분한 증거들을 나열했습니다. 마지막으로 한 문장만 덧붙이자면, 성숙한 에이전트의 심장박동은 다중 턴 상태, 입력 거버넌스, 스트리밍 소비, 인터럽트 원장, 그리고 {완료, 실패, 복구, 계속} 간의 구분을 동시에 제어할 수 있어야 합니다. 이러한 구조가 결여된 시스템은 여전히 멋진 데모를 만들어낼 수는 있겠지만, 그것은 런타임이라기보다 일회성 연극에 가깝습니다.

다음 장에서는 이 심장박동이 외부 세계와 가장 직접적으로 맞닿는 지점인 도구, 권한, 그리고 인터럽트에 대해 논의하겠습니다. 이번 장에서는 루프가 왜 존재하는지 설명했으니, 다음 장에서는 루프가 일단 도구를 가지게 되면 왜 절제를 배워야 하는지 설명하겠습니다.
